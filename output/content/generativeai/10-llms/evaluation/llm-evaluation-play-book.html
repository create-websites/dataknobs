00Executive brief

LLM evaluation is a measurement system, not a one-time leaderboard check.

An LLM that sounds convincing may still be wrong, miss a critical instruction, leak sensitive information, take an unauthorized action or become too costly at scale. Evaluation converts those possibilities into defined scenarios, repeatable tests, trustworthy measurements and operational decisions. Testing should be tailored to the use case and repeated as the model, data, prompts, tools and users change.

The operating principle

A useful evaluation answers five questions: Does the system do the task? Can we trust the answer? Can it fail safely? Does it perform across relevant users and edge cases? Is it worth the latency and cost?

What this playbook gives your team

  • A single evaluation vocabulary: what to measure at the model, workflow, retrieval, tool, user and business levels.
  • A repeatable operating cycle: design test cases, label ground truth, grade outputs, compare versions, approve releases and monitor drift.
  • Risk-based assurance: hard controls for severe failures plus quantitative quality and reliability targets for each use case.
  • Practical assets: example scorecards, dataset schema, judge rubric, red-team plan, evaluation charter, release checklist and ownership model.

Five non-negotiables

01

Measure the full application, not only the base model. The prompt, retrieval layer, permissions, tools and UI can create failures independently.

02

Keep tests representative and adversarial. Include ordinary use, important subgroups, edge cases, ambiguous inputs and attacks.

03

Use multiple graders. Combine rules, reference-based checks, human review and carefully calibrated model judges.

04

Separate quality scores from safety gates. An overall average must never hide a critical privacy breach or unauthorized action.

05

Treat an evaluation as a living product. Version datasets, prompts, judges and thresholds, and feed real failures back into the suite.

Part I / Foundations

Set the direction

Design evaluation around user outcomes, measurable risks and accountable release decisions.

01Why evaluate?

Recommended statement

Careful, continuous evaluation is the foundation of trustworthy AI. It helps teams build systems that are useful, accurate, safe and honest about uncertainty, while creating the evidence needed to improve them. Evaluation reduces risk; it does not guarantee perfection.

Three ways to communicate the purpose

FramingMessageWhen to use
ConciseTest AI systematically so it is more useful, accurate and safe.Slide headlines and product pages
ExpandedThorough evaluation checks whether an AI system meets real user needs, follows constraints, limits harmful behavior and stays dependable as it changes.Executive and governance discussions
BenefitsEvaluation reveals errors, bias, unsafe behavior and operational waste, so teams can prioritize improvements with evidence rather than intuition.Engineering and investment decisions

The three core pillars

PillarPrimary questionExample evidence
AccuracyIs the answer or action correct for the task and supported by facts?Reference match, factual claim verification, citation validity, task success
SafetyDoes the system respect policy, user permissions and the limits of its authority?Critical-incident count, attack resistance, privacy leakage, safe refusal
ProgressWhat improved, degraded or remains uncertain between versions?Regression delta, paired comparison, trend by error category, cost/quality trade-off

Broader value beyond the three pillars

  • User trust: fewer unsupported confident statements, more appropriate clarification and abstention.
  • Operational reliability: fewer failed calls, timeouts, malformed outputs and cascading errors.
  • Fairness and inclusion: better behavior across languages, accessibility needs and relevant population slices.
  • Cost discipline: measure quality per dollar, token use, p95 latency and human review burden.
  • Governance and auditability: evidence for why a model or workflow was approved, restricted or rolled back.
Important distinction

An accurate answer may be unsafe (e.g., revealing protected data). A safe refusal may be unhelpful if a benign question should have been answered. Measure both under-refusal and over-refusal, not a single safety score.

02Define the object of evaluation

Choose the boundary of each test. An LLM application is a stack; the same model may behave differently after changes to instructions, retrieval, routing, permissions, tool schemas or the conversation state.

LevelWhat to testTypical failure
Base modelReasoning, knowledge, language, formatting, policy behavior under controlled promptsIncorrect reasoning despite a good application prompt
Prompt / policySystem instructions, rubric compliance, structured output, refusalsA prompt edit breaks required JSON or tone
Retrieval / RAGSearch, filtering, ranking, citations, grounded synthesisCorrect source exists but is not retrieved
Agent / tool layerPlanning, API choice, arguments, permissions, execution, recoveryAgent calls the right tool with the wrong user ID
End-to-end productTask completion, UX, latency, cost, logs, escalationA good model output never reaches the user
Human-in-the-loopReviewer burden, override quality, handoff and appealsHigh-risk case auto-approved without reviewer

Offline, shadow, online and human evaluation

Offline / pre-deployment

Frozen dataset, fixed model versions and repeatable comparisons. Best for regression and controlled research.

Shadow / replay

Candidate workflow runs on sampled production-like traffic without affecting the user or taking live actions.

Online monitoring

Observe real requests using logged signals, sampled review, user feedback and targeted judges.

Controlled experiment

Compare real user outcomes across randomized variants when safety gates are already satisfied.

Human expert review

Resolve nuance, policy ambiguity, severe cases and calibration disagreements.

03Classify risk before selecting metrics

A model that formats meeting notes and an agent that changes customer entitlements should not share one approval threshold. Set risk based on impact of a wrong output, autonomy, access to sensitive information, reversibility and scale. The following is an illustrative operating taxonomy, not a legal classification.

R1Low
Characteristics

Creative ideation or formatting; limited downstream impact.

Required assurance

Task quality, UX, baseline safety, cost, sampled spot checks.

R2Moderate
Characteristics

Customer-facing Q&A or internal summarization; errors cause friction.

Required assurance

Representative gold set, policy tests, groundedness, slice reporting, review process.

R3High
Characteristics

Financial, health, legal or sensitive enterprise workflows; material consequences.

Required assurance

Domain expert labels, strict critical-event gates, calibrated judges, audit logs, rollback.

R4Critical
Characteristics

Autonomous actions with privileged access or hard-to-reverse effects.

Required assurance

Explicit authorization, least privilege, sandbox red teams, independent review, fail-safe controls.

Risk acceptance belongs to a named owner

For every evaluation charter record the system owner, product owner, evaluation lead, policy/security owner, domain approver and on-call operator. The engineering team recommends readiness using evidence; accountable owners accept residual risk. If no one can sign the decision, the process is incomplete.

Part II / Design

Build an evaluation that can be trusted

The quality of your conclusions depends on the quality of your scenarios, labels, graders and comparisons.

04The eight-step evaluation lifecycle

  1. Define the job and unacceptable failures. Translate vague goals ("be accurate") into observable behaviors and user harm scenarios.
  2. Set scope, risk tier and slices. Specify audiences, languages, topics, permissions, environments and excluded uses.
  3. Assemble and version a representative test set. Include production-derived, synthetic, edge and adversarial cases with provenance.
  4. Specify gold references and rubrics. Document allowed answers, forbidden behaviors, acceptable abstentions and severity.
  5. Choose and calibrate graders. Select deterministic checks, code execution, human review and/or LLM judges appropriate to each metric.
  6. Run a reproducible comparison. Pin model/prompt/retrieval/tool versions; capture traces, metadata, cost and repeated runs.
  7. Analyze slices, uncertainty and failure modes. Compare against the baseline and gates; inspect cases instead of trusting only the mean.
  8. Decide, deploy, monitor and learn. Approve, restrict, canary or reject. Turn incidents and user feedback into new regression tests.
Evaluation contract

Treat each test like a contract: input + context + expected behavior + scoring rule + severity + owner + evidence. A score without a defined contract is a weak signal.

Start from actual tasks, not abstract scores

For a support bot, success may mean an accurate resolution with an appropriate escalation. For a risk analyst, it may mean extracting all qualifying entities without fabricating details. For an agent, success may mean producing the correct approved artifact while avoiding any unapproved write. The same general-purpose benchmark cannot represent all three.

05Construct evaluation datasets and test suites

An evaluation suite is a curated, versioned collection of test cases. Build separate suites for release gating, red teaming, exploration and production replay. Keep a sealed holdout so that prompt improvements are not repeatedly tuned to the same questions.

SuitePurposeSuggested content
SmokeFast CI signal for broken integrations10–30 canonical requests, valid JSON, routing, permissions
RegressionDetect changes in known good behavior100–500 important gold cases, recurring defects, key slices
CapabilityTrack relevant task quality and breadthDomain reasoning, grounded answers, complex workflows
Safety / red teamExercise failure boundaries and misusePrompt injection, leakage, role spoofing, harmful requests
Stress / robustnessChallenge unexpected inputs and volumeLong inputs, typos, language shift, outages, concurrency
Production replayMatch changing real-world demandDe-identified sampled traces with permissions and retention controls
Sealed holdoutIndependent confidence before approvalHidden balanced set not used in prompt or judge development

Design a coverage matrix

Cross several dimensions rather than collecting only easy questions: intent, complexity, document/source type, language, jurisdiction, user role, sensitivity, freshness, conversation length, tool path, expected answer type and failure severity. Track the number and weight of cases in each relevant slice.

SliceEasy caseHard or edge case
KnowledgeQuestion answered in a single documentConflicting versions, no source, misleading outdated source
LanguageStandard EnglishSpelling noise, code-switching, locale-specific phrasing
PermissionsAuthorized user reads own dataCross-tenant request, revoked permission, role spoofing
ConversationSingle clear questionContradictory follow-up, long memory, changing constraints
ActionSingle read-only API callMulti-tool plan, partial failure, retry, idempotency
SafetyClearly disallowed requestIndirect injection inside retrieved content, borderline policy case

Data sourcing and contamination controls

  • Prefer consented or authorized real task traces over purely synthetic examples for representative quality measurement.
  • De-identify and minimize private data before collection; preserve protected original data only in approved, access-controlled systems.
  • Use synthetic data to fill rare edge cases, then validate realism with a domain expert. Tag every case with its origin.
  • Deduplicate near-identical prompts, use entity/time splits when applicable and test for accidental overlap with training/tuning examples.
  • Keep train/development evaluation, release regression and sealed holdout distinct. Record who can view or edit each.
  • Do not upload confidential source documents to external graders without approved contractual and technical controls.

How many examples?

There is no universal sample size. Start small to discover systemic failures, then size the formal suite around the precision you need for decision-making and the frequency of rare harms. For instance, zero observed failures in 100 trials does not demonstrate a zero failure probability; the rough "rule of three" yields an approximate 95% upper bound near 3/100 for independent Bernoulli trials. See the statistics section for caveats.

06Write gold answers and annotation rules

A reference answer is not always one ideal paragraph. Some tasks admit multiple valid responses, and many allow an explicit "I do not know". Specify factual claims and required fields separately from surface wording; keep policy decisions and correctness checks distinct.

Human labeling standard operating procedure

  1. Write a clear annotation manual with definitions, positive and negative examples and a policy escalation path.
  2. Run a pilot: two independent annotators label an overlapping sample and explain disagreements.
  3. Adjudicate ambiguous cases with a qualified reviewer and revise the manual before scaling.
  4. Measure agreement by label type (e.g., raw agreement; kappa where appropriate), not just a single aggregate.
  5. Keep the raw labels, adjudicated label, justification, cited evidence, annotation date and author role.
  6. Review high-disagreement, high-impact and evolving-policy cases at each major release.
Avoid false ground truth

When the source corpus itself is wrong or outdated, a model can faithfully reproduce the source and still produce a false real-world answer. Distinguish source-groundedness from real-world factual correctness.

07Select graders and calibrate the judge

Different questions require different methods. Combine automated tests that are precise and cheap with human judgment where context, nuance or potential harm demands it.

GraderBest forLimitations / control
Exact / schema / regexIDs, classification labels, JSON, citations, refusal tokensCan penalize equivalent wording; must validate semantics separately
Code / executionSQL correctness, API argument constraints, generated codeSandbox external effects; success tests may not capture harms
Reference / semanticMeaning similarity, answer consistencySimilarity can hide factual reversals or unsupported details
LLM-as-judgeOpen-ended quality, faithfulness, instruction adherencePosition/verbosity/self-preference bias; calibrate to experts
Expert humanHigh-stakes correctness, ethics, borderline safetyCostly, variable; use training, calibration and adjudication
User / businessResolution, adoption, corrections, escalationAffected by UX, selection bias and confounding

Judge design rules

  • Grade one dimension at a time with explicit behavioral anchors and allow "insufficient evidence".
  • Give the judge only necessary references and source context; do not allow it to invent missing facts.
  • Require a structured result: verdict, score, cited evidence or reason, confidence flag and error category.
  • Use a separate evaluation model/configuration when possible, and record its version and settings.
  • For pairwise comparison, randomize A/B order; include a subset with reversed order to measure position bias.
  • Run repeat judgments on borderline cases; compare judge decisions against adjudicated human labels by slice.
  • Quarantine model outputs containing embedded grader instructions; user/generated content is data, not an instruction to the judge.
Four-point anchored rubric (0–4)
ScoreInterpretationAnchor
0 · FailViolates a hard constraint or does not complete the taskWrong fact, invalid action, prohibited disclosure, no answer
1 · PoorMajor gaps; user cannot rely on the resultCentral claim unsupported or required step missing
2 · PartialUseful elements but still needs material correctionSome facts right; omission or ambiguity affects outcome
3 · GoodCorrect, complete and appropriate for the taskMeets mandatory criteria with minor nonmaterial issues
4 · ExcellentCorrect and clear with traceable supportMeets all criteria efficiently, communicates uncertainty

Calibration exercise. Label 50–100 representative cases independently, compare judge and expert labels with a confusion matrix, inspect false passes/false fails, modify the rubric, then validate on cases that were not used during rubric editing. For safety-critical classes, optimize against missed severe violations rather than raw overall agreement.

08Analyze uncertainty and comparative evidence

An average score is a noisy estimate. The unit of analysis should match the user journey (e.g., user or conversation, not a thousand correlated turns from one customer). Report uncertainty and both absolute and relative differences.

Essential formulas and interpretation
MeasureHow to calculateImportant caution
Pass ratepassed cases / eligible casesSpecify treatment of abstentions, missing outputs and timeouts
PrecisionTP / (TP + FP)A high value can coexist with many missed positives
RecallTP / (TP + FN)Critical when missing a true case carries a high cost
F12 × precision × recall / (precision + recall)Not cost-sensitive; can hide class prevalence shifts
Regression deltacandidate metric − baseline metricUse same cases and versions; report paired uncertainty
p95 latency95th percentile of end-to-end user latencySeparate model, retrieval, tools and network time
Cost per successtotal variable cost / completed valid tasksInclude re-tries, judges and human review where relevant

What confidence really means

  • For binary pass/fail rates, prefer a binomial confidence interval such as Wilson rather than treating a point estimate as exact.
  • For paired candidate-versus-baseline outputs, bootstrap by independent unit (case, user or session as appropriate) and report an interval for the difference.
  • Prespecify a primary metric and guardrails. If you inspect dozens of metrics or repeatedly peek at data, consider multiplicity and sequential testing.
  • Report per-slice sample size and uncertainty. A 100% rate on four cases says little about production reliability.
  • For rare critical events, combine targeted adversarial testing, scenario analysis and independent controls; ordinary traffic samples may not reveal a meaningful rate.
  • Record judge variance and annotation uncertainty, not just model-output variance.
Illustrative finding

Candidate answers improved from 82% to 87% overall on a 300-case paired suite. This may be promising, but promotion still requires: the uncertainty interval for the paired difference, no unacceptable safety regressions, acceptable slice results and verification that the improvement is not caused by judge drift.

Part III / Measure

Evaluate the whole capability and risk surface

Translate quality, safety and operational requirements into observable metrics and failure investigations.

09The metric taxonomy: what good looks like

Use a portfolio of measures. Primary outcome metrics answer whether the system accomplished the job. Diagnostic metrics explain the failures. Guardrails capture conditions that must not worsen or cross a limit.

DimensionMeasureFailure it reveals

Safety & privacySevere-incident count, leakage rate, unsafe compliancePolicy violation or disclosure

How to choose the primary metric

Choose one outcome metric closely connected to the user job, a small set of supporting diagnostics and non-negotiable guardrails. Avoid replacing a meaningful outcome with a broad composite: an 86/100 "AI quality score" is uninterpretable unless definitions, weights, slices and hard gates are visible.

A clear pass/fail definition

For a research answer, "pass" might mean: all requested items covered; every factual claim supported by current approved sources; no material contradiction; no leakage; and correct uncertainty when evidence is insufficient. Surface-level fluency is not proof.

10Evaluate retrieval-augmented generation (RAG)

RAG systems can fail when they retrieve the wrong context or when the generator misuses the right context. Evaluate retrieval and synthesis separately before assessing end-to-end usefulness. Metrics such as context precision, context recall, faithfulness and response relevancy are implemented in RAG evaluation frameworks such as Ragas, but definitions can vary by implementation.

RAG stage-by-stage evaluation
StageRecommended checkDiagnostic question
Corpus ingestParsing coverage, document freshness, lineageDid a table, heading, scan or version get lost?
Access filteringACL recall, cross-tenant isolation, deny testsDid unauthorized chunks enter retrieval?
RetrievalRecall@k, relevance@k, source diversityWas the answer-bearing evidence found?
RerankingMRR, nDCG, context precisionAre the strongest passages near the top?
GenerationClaim-level support, completeness, correctnessDid it use context without inventing?
CitationsReference validity and entailmentDo citations actually support the adjacent claim?
No-answer pathSelective accuracy, abstention appropriatenessDid it say "not enough evidence" when required?

Make the key distinctions explicit

  • Retrieval recall@k: percentage of answer-bearing relevant items retrieved within the top k; meaningful only when relevant-item labels are defined.
  • Retrieval precision@k: percentage of the top k retrieved items that are relevant to the request.
  • MRR / nDCG: ranking-sensitive retrieval measures; useful when high-ranked evidence matters.
  • Faithfulness / groundedness: whether the answer claims follow from provided source material; a claim can be grounded in a bad source and still be wrong in reality.
  • Answer correctness: whether response facts match an independent, trusted reference; not equivalent to groundedness.
  • Citation precision: fraction of cited claims whose linked source actually supports them, checked near the claim rather than merely in the document.
  • Citation recall: fraction of source-requiring material claims that include sufficient source support.
  • Appropriate abstention: refuse to invent an answer when evidence or permission is missing; distinguish from unnecessary refusal.

Example: a policy bot changes its answer after corpus updates

Scenario: a customer asks whether a plan can be canceled within 30 days. The old policy says 14 days; the current document says 30. A correct evaluation should require the current version, confirm source effective date, check cited text and ensure the answer does not splice exceptions from the obsolete document.

Diagnostic sequence: (1) inspect corpus freshness, (2) confirm permissions, (3) check ranked chunks, (4) inspect generated claims, (5) validate citation spans, (6) compare supported answer with the current gold reference, (7) add the regression case.

RAG hard gate

For a sensitive corpus, a cross-tenant retrieval or disclosure is a security failure regardless of groundedness score. Do not allow high answer quality to offset an authorization breach.

11Evaluate tool-using agents and multi-step workflows

An agent should be measured by the final authorized outcome plus the safety and efficiency of its trajectory. A coherent final message cannot excuse an unauthorized intermediate tool call. Simulate or sandbox side effects for repeatable evaluation, and capture traces with every decision boundary.

Four layers of agent evaluation
LayerExamples of measuresKey control
PlanCorrect decomposition, adherence to order/constraintsDo not assume the shortest plan is always safest
Tool choiceCall necessity, tool precision/recall, schema-valid argsLeast privilege; allow-listed tools and accounts
ExecutionSuccessful API response, idempotency, retry and rollbackNo unintended or irreversible side effects
OutcomeBusiness goal reached, artifact quality, user approvalExplicit confirmation for consequential actions

Adversarial agent scenarios to include

  • Prompt injection via tools: a retrieved webpage tells the agent to override policy or reveal secrets.
  • Identity and permission confusion: user asks to modify another customer account; tool scopes must block it.
  • Tool output tampering: an API returns suspicious instructions inside data fields.
  • Failure recovery: the second tool fails after the first write; agent must compensate or escalate.
  • Double action: a retry must not submit duplicate orders, payments or notifications.
  • Confirmation bypass: agent proceeds with a financial or destructive action before explicit user approval.
  • Memory poisoning: a prior message inserts a future instruction that conflicts with current authorized policy.
  • Runaway budget: model loops through tools, causing excessive cost or external calls.

Trajectory scoring rubric

Record the expected state transition, allowed tools, forbidden tools, allowed arguments, required user approval, state after execution and rollback outcome. Do not mark a run successful merely because it eventually reached a target after violating a required intermediate safeguard.

Multi-turn conversational evaluation

For multi-turn systems, test whether the system remembers only authorized context, resolves follow-up references, respects updated constraints, asks clarifying questions when essential and avoids propagating earlier incorrect assumptions. Use whole-conversation cases with a single business outcome plus turn-level diagnostics.

12Safety, security and privacy evaluation

Safety testing covers model responses and infrastructure controls. The current OWASP Top 10 for LLM Applications 2026 and its companion Top 10 for Agentic Applications are useful references for threat modeling; this playbook translates threat categories into testable controls instead of treating a risk list as a substitute for a security program.

2026 noteThe 2026 OWASP LLM list keeps all ten categories but reorders them: prompt injection stays first, excessive agency moves up to third, and "system prompt leakage" is broadened into hidden context exposure. OWASP frames the LLM list for a model acting as a component and directs teams to the Agentic list once the model gains tools, memory and authority to act.

Severity assignments should be approved locally by security, legal, policy and domain owners. Sampling is not sufficient to establish safety for rare high-severity classes; also test architecture controls (ACL, validators, approval prompts, audit logging) directly.

Privacy and sensitive-data handling

  • Minimize what is stored in evaluation traces; pseudonymize where possible and protect reidentification keys separately.
  • Define approved data region, retention, legal basis, access roles, vendor/subprocessor handling and deletion workflow.
  • Test prompt, completion, retrieval and tool logs for accidental credential or personal-data inclusion.
  • When testing injection or leakage, use seeded synthetic canary secrets rather than real production credentials.
  • Enforce authorization in backend services, not with a prompt that merely says "do not reveal".
  • Include security review before sending internal cases to a third-party judge or evaluation service.

13Fairness, robustness, accessibility and uncertainty

Overall accuracy can hide systematic underperformance. Select slices based on product reach, risk, known failure modes and applicable obligations; do not infer or retain sensitive characteristics unnecessarily. Evaluate accessibility of the full product experience as well as response text.

Representative robustness tests

  • Paraphrase stability: equivalent questions should yield compatible facts and actions, allowing stylistic variation.
  • Out-of-distribution inputs: unfamiliar topics, corrupted files, unusual document layouts and unexpected API values should fail gracefully.
  • Temporal robustness: changed policies, new data and expired documents should trigger source/version checks.
  • Multilingual and locale: test target languages, numerals, dates, names, local units and low-resource terminology.
  • Accessibility: simple language when requested, usable headings, no color-only meaning, screen-reader-compatible outputs and tables.
  • Fairness: compare outcome quality and harms across legally and ethically appropriate, consented or otherwise authorized slices.
  • Uncertainty calibration: score whether the model knows when to ask, qualify, abstain or escalate instead of sounding confident.

Reporting slice gaps

Present both overall score and relevant group-level score with sample sizes. Example: overall answer correctness 92%, but only 77% on long scanned contracts (n=45). A weighted overall number alone would conceal the issue. Small groups should be interpreted with wide intervals and appropriate privacy safeguards.

14Evaluate latency, cost, reliability and human experience

A product is only useful if it works under real load and within a sustainable budget. Measure the complete user-visible interaction, including retry, retrieval, tool execution, guardrails and post-processing.

Quality-cost frontier

Compare candidate architectures on a Pareto frontier: quality versus dollars per successful task, latency and operational risk. A cheaper model is a win only if it meets hard constraints and preserves required task quality. Consider tiered model routing, caching, retrieval pruning and selective human review; re-evaluate after every optimization.

15Use public benchmarks as supporting evidence

Public benchmarks help screen candidate base models and identify general strengths, but they rarely represent your data, permissions, workflow or user population. For example, HELM emphasizes multiple metrics and scenarios; SWE-bench evaluates software patch resolution in controlled environments. Benchmark implementations and rankings evolve, so freeze exact versions when comparing.

Benchmark rule

A public leaderboard can inform model selection. A domain-specific end-to-end suite and a release gate should determine whether your application ships.

Part IV / Operate

Turn evaluations into an engineering discipline

Make evidence reproducible, release decisions auditable and failures actionable in production.

16Reference architecture for an evaluation platform

An evaluation platform should orchestrate test data, candidate versions, graders, traces, metrics and decisions rather than be a collection of spreadsheets. Model-provider independence and versioned artifacts make comparisons more reliable.

Recommended logical components

  1. Use-case / risk registry. Application purpose, owner, risk tier, policy boundaries, mandatory metrics and release gates.
  2. Dataset registry. Case IDs, consent/provenance, source snapshot, dataset version, slices, access classification and gold labels.
  3. Target and configuration registry. Model identifier, prompt hash, generation settings, RAG index, tool schemas, feature flags and release commit.
  4. Eval runner. Executes offline/replay/agent simulations with pinned inputs, controlled seeds where applicable, retries and cost budgets.
  5. Trace and artifact store. Prompt/response, retrieved chunks, tool events, guardrail results, timestamps and output hashes under access controls.
  6. Grader service. Deterministic functions, domain reference checks, calibrated model judges and human-review queues.
  7. Metrics and analysis. Per-slice scores, paired comparisons, confidence intervals, severity incidents, regression diffs and failure clustering.
  8. Decision engine. Policy gates, approvals, waivers, promotion status, audit trail, canary and rollback triggers.
  9. Monitoring and feedback. Production sampling, user corrections, incidents and dataset refresh into future evaluation runs.

Safe execution architecture

Run adversarial and action-oriented tests in isolated environments with fake credentials and fixture data. Use short-lived tokens, outbound allowlists, action approval gates and an immutable action log. Sampling production conversations for evaluation must comply with privacy and security rules.

Mapping to a KREATE / KONTROLS / KNOBS implementation

One practical product architecture is to use KREATE for model/data/workflow assets, KONTROLS for policy, privacy and release conditions, and KNOBS for evaluation, A/B experimentation and improvement measurement, as in the DataKnobs product suite. A shared run ID can connect deployed model configuration, exposure, scored trace, gate decision and resulting user outcome. This is a proposed implementation pattern, not a requirement of the framework.

17Release gates, regression testing and model upgrades

Release decisions should be based on a multidimensional scorecard plus hard-fail controls. Do not accept a single weighted average if a critical class has failed or an important segment has regressed.

Four possible decisions

PROMOTE

All gates pass

Gain is material or a documented strategic trade-off. Evidence: signed scorecard + release hash.

CANARY

Passes severe gates

Remaining risk is bounded and monitored. Evidence: traffic limit, alert thresholds, exit/rollback trigger.

HOLD

Uncertain or remediable

Quality uncertainty or remediable regression exists. Evidence: issue owner, due date and rerun plan.

REJECT / ROLLBACK

Critical fail

Critical fail or unacceptable decline. Evidence: incident record and rollback verification.

What changes should trigger evaluation?

  • Model/provider release, context-window or decoding changes; prompt and policy edits.
  • Retriever, embeddings, chunking, reranker, index or corpus freshness changes.
  • Tool schema, permissions, agent planning, memory, system prompt or UI handoff changes.
  • Data classification or downstream workflow changes; expansion to new languages or audiences.
  • An incident, unexpected user feedback, monitoring drift or severe third-party vulnerability.

Sampling strategy

  • Continuously monitor deterministic safety and system-control signals wherever feasible.
  • Apply stratified quality sampling across intent, risk tier, channel, model version and important user groups.
  • Oversample failed tools, thumbs-down feedback, long conversations and high-risk outcomes for investigation; report sampling weights separately.
  • For expensive LLM judges, combine a low baseline sampling rate with targeted event-triggered scoring.
  • Escalate ambiguous or severe findings to humans; protect evaluation traces with data minimization and retention limits.
  • Convert resolved incidents into regression tests, then rerun the suite before the next release.

Drift is more than model drift

The prompt may be unchanged while the corpus, API output, user goals, policy interpretation or language distribution shifts. Build drift alerts for input distribution, retrieval source mix, document age, tool failure and output quality. Investigate root causes before automatically updating thresholds.

19Compare variants with A/B testing and experiments

Offline scores measure what a system can do in controlled cases; an online experiment measures what changes for actual users. Use experimentation only after mandatory risk controls pass. Pre-register the primary user outcome and guardrails, then connect exposure and outcome events reliably.

Experiment design checklist

  1. Define the unit of randomization (usually user or account); assignment must be stable across visits and devices when appropriate.
  2. Document eligibility, treatment, baseline, power assumptions, duration, pre-registered hypothesis and stopping rule.
  3. Emit exposure only when the assigned experience is actually delivered, not merely on assignment.
  4. Instrument outcome windows (task resolved, successful action, correction or escalation) and guardrail metrics.
  5. Check for sample-ratio mismatch and event-integrity issues before interpreting business effects.
  6. Use a suitable analysis for binary, continuous or count outcomes; handle repeated users and sequential monitoring correctly.
  7. Inspect per-slice risks and guardrails. A global win does not authorize a treatment that harms a protected or high-risk pathway.
  8. Decide: keep baseline, promote, extend with planned rules or stop for safety. Archive version and analysis.

Typical experiment example

Hypothesis: retrieval reranker B improves verified answer completion relative to A. Primary outcome: user questions resolved without correction. Guardrails: citation support, severe policy incidents, p95 latency and cost per resolved task. Mechanism measures: answer-bearing recall@5 and unsupported-claim rate. The mechanism explains why an effect happened; it does not replace the outcome.

Statistical pitfalls to avoid

  • Peeking at nominal p-values every hour without a sequential method can inflate false positive risk.
  • Sharing the same users across variants or reassigning them can contaminate outcomes.
  • Differences in exposure logging can create artificial conversion lift.
  • Optimizing many metrics and selecting the biggest apparent win invites multiple-comparison bias.
  • Significant does not equal important: report effect size, uncertainty, cost and operational value.

20Red teaming, triage and incident response

Red teaming deliberately seeks failures beyond ordinary tasks. Run it before high-risk releases, after meaningful architecture changes and periodically against new threat patterns. Distinguish discovered vulnerabilities from confirmed production incidents.

A focused red-team program

  1. Create a threat model: assets, actors, permissions, external content, tools and most damaging possible failures.
  2. Design an attack matrix with entry points (user prompt, file, retrieval chunk, webpage, API/tool response and memory).
  3. Use synthetic canary secrets, benign simulated side effects and isolated test accounts.
  4. Generate attacks with both humans and controlled automated mutation; record which payload, tool and version were used.
  5. Validate a suspected success against independent evidence rather than trusting an attack-generator claim.
  6. Assign severity and exploitability; fix root controls (ACL, approval, output validation) as well as prompts.
  7. Re-run the identical cases and nearby variants; add enduring regressions and update security documentation.

Failure handling principle

If an evaluator reports a possible sensitive-data leak, treat it as an investigation trigger, not conclusive proof. Validate securely; if confirmed, follow the severity policy and incident procedure.

23Worked example: complaint classification and extraction

The job

A system classifies whether an interaction contains a customer complaint and extracts product, reason and supporting evidence. A false negative may prevent a valid complaint from being routed for review; a false positive increases manual work. The threshold should reflect cost of error, not just overall accuracy.

OutcomeNumberInterpretation
True positive (TP)177Complaint correctly detected
False positive (FP)23Not a complaint, but flagged
False negative (FN)13Complaint missed : inspect severity and policy impact
True negative (TN)787Noncomplaint correctly rejected
88.5%Precision · 177 / 200
93.2%Recall · 177 / 190
96.4%Accuracy · 964 / 1,000
97%Recall floor · fails

In this example, precision = 177 / (177 + 23) = 88.5% and recall = 177 / (177 + 13) = 93.2%. Accuracy would be 96.4%, which could conceal the 13 missed complaints. If the approved recall floor is 97% on the high-risk slice, this candidate fails that gate even though accuracy looks strong.

Operational metrics and checks

  • Report confusion matrices by product, call channel, language, complaint severity and data freshness.
  • Evaluate extraction fields separately: product classification, issue code, quoted evidence, completeness and schema validity.
  • Calibrate scores to guide human review; the meaning of 0.8 confidence must be tested against actual outcomes.
  • Use threshold selection curves: false-negative cost, review capacity and precision/recall trade-off.
  • Track reviewer overrides and investigate systematic disagreement rather than assuming model confidence equals truth.
  • Ensure complaint-relevant time windows, user identity and data access comply with operational and legal requirements.

Example failure-to-fix loop

An issue is missed because the customer uses sarcastic wording without the word "complaint". Add it to an annotated error cluster, test semantically similar examples, revise instructions/labels or classifier design, then rerun the full suite and compare false-positive cost. Do not change the threshold based on a single case.

?Frequently asked questions

What is LLM evaluation?

A measurement system that converts possible failures of an AI application into defined scenarios, repeatable tests, trustworthy measurements and operational decisions. It should be tailored to the use case and repeated whenever the model, data, prompts, tools or users change.

What are the three core pillars of LLM evaluation?

Accuracy (is the answer or action correct and supported by facts), safety (does the system respect policy, permissions and the limits of its authority) and progress (what improved, degraded or remains uncertain between versions).

What is the difference between groundedness and answer correctness?

Groundedness checks whether claims follow from the supplied sources; answer correctness checks them against an independent, trusted reference. A claim can be grounded in an outdated source and still be false, so measure both.

How many test cases does an evaluation suite need?

There is no universal number. Start small to find systemic failures, then size the suite for the precision your decision needs. Zero failures in 100 independent trials only bounds the failure rate near 3% at about 95% confidence.

How do you calibrate an LLM-as-a-judge?

Have experts label 50–100 representative cases, compare with the judge via a confusion matrix, inspect false passes and false fails, revise the rubric and validate on fresh cases. For safety-critical classes, optimise against missed severe violations.

How should AI agents be evaluated?

On the final authorized outcome plus the safety and efficiency of the trajectory, across plan, tool choice, execution and outcome. An unauthorized intermediate call is a failure even if a server-side control blocked it.

What release decisions should an evaluation produce?

PROMOTE, CANARY, HOLD or REJECT/ROLLBACK, each backed by specific evidence such as a signed scorecard, canary limits, a rerun plan or an incident record.

Are public benchmarks enough to decide whether to ship?

No. Benchmarks such as HELM, MMLU-Pro or SWE-bench help screen base models, but a domain-specific end-to-end suite and a release gate should decide whether your application ships.

Final reminder

Evaluation maturity is demonstrated when a team can reproduce a failure, identify the failed contract, explain its impact, block unsafe releases and show measured improvement in real user outcomes. The objective is not the highest score; it is a better-governed and more dependable AI product.
