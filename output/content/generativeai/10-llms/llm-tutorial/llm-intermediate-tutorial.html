LLM Intermediate Tutorial: Practical Use of LLMs

Article

Detailed explanation

The content below expands on the slides with structured HTML article content.

Beginner material explains what a large language model is. This tutorial is about making one do useful work. It covers six practical areas in order: building a simple LLM application, embeddings and vector databases, retrieval-augmented generation, evaluating what the model produces, the prompt engineering techniques that matter in production, and building agents. It assumes you know what tokens, context windows, and system prompts are, and that you can write code in some language.

Part 1 : Building Simple LLM Apps

Almost every LLM product, however elaborate, is built from one primitive: an HTTP request carrying messages, returning generated text. Get comfortable with that request and everything else is composition.

How to call an LLM API

The major providers : OpenAI, Anthropic, Google, Mistral, and the hosting services that serve open-weight models : have converged on a similar shape. You send a model identifier, a list of messages, and some generation parameters. You get back generated text plus token usage.

A typical request body looks close to this:

{
  "model": "some-model-identifier",
  "max_tokens": 1024,
  "temperature": 0.2,
  "system": "You are a concise technical assistant.",
  "messages": [
    { "role": "user", "content": "Summarize this changelog in three bullets." }
  ]
}

Details vary. Some providers carry the system prompt as a top-level field, others as the first message in the array. Some require max tokens, others default it. Authentication is a bearer token or an API key header in essentially all of them. Use the official SDK rather than raw HTTP where one exists : it handles retries, streaming, and response parsing that you would otherwise write yourself.

Four things to get right from the first request:

  • Keep keys server-side. An API key in client-side JavaScript or a mobile binary is a key someone else will spend. Route calls through your own backend.
  • Handle failure properly. Rate limits, overload responses, and timeouts are normal operating conditions, not exceptions. Retry with exponential backoff and jitter, and cap the retries.
  • Stream for anything interactive. Streaming responses arrive token by token over server-sent events. Time-to-first-token is what users perceive as speed, and it is dramatically better than waiting for a complete response.
  • Log usage from the start. Every response reports input and output token counts. Record them alongside the request so cost attribution exists before you need it, not after a surprising invoice.

Chat vs. completions endpoints

You will meet two API styles, and the distinction is partly historical.

The older completions endpoint takes a single string and continues it. You send raw text, the model appends more text. There are no roles and no conversational structure : any structure you want, you build by hand inside the prompt string. It maps directly onto what a base model does.

The chat endpoint takes a structured list of messages, each tagged system, user, or assistant, and returns an assistant message. This matches how instruction-tuned models were actually trained, which is why it produces better results on nearly every task. It is also what tool calling, structured output, and multimodal input are built on.

For new work, use the chat endpoint. Completions endpoints are deprecated or de-emphasized almost everywhere and are only worth reaching for in narrow cases : raw text continuation, or fill-in-the-middle code completion where a specialized model expects a prefix and suffix rather than a conversation.

A related distinction worth knowing: several providers now offer a stateful "responses"-style endpoint that retains conversation server-side so you send only the new turn rather than the whole history. It reduces bandwidth and simplifies client code, at the price of storing conversation state with the provider. The stateless chat endpoint remains the portable default.

Basic conversation memory

The model is stateless. It has no recollection of the previous turn. Conversational continuity is an illusion you create by resending the history on every request:

messages = [
  { "role": "user",      "content": "What is HNSW?" },
  { "role": "assistant", "content": "HNSW is a graph-based index for..." },
  { "role": "user",      "content": "How is it different from IVF?" }
]

That second question is only answerable because the first exchange rides along with it. Which means conversation memory is fundamentally a context-budget problem: every turn makes the next request longer, slower, and more expensive, until the history no longer fits.

Four strategies, in ascending order of sophistication:

  • Sliding window. Keep the system prompt plus the last N turns and discard the rest. Trivial to implement, and adequate for short task-focused sessions. The failure is abrupt: something said early simply vanishes.
  • Summarization. When history exceeds a threshold, have the model compress older turns into a running summary and prepend that. Retains the gist at a fraction of the tokens. Details erode with each round of compression, so keep the most recent turns verbatim.
  • Structured state extraction. Rather than summarizing prose, extract the facts that matter : user name, chosen plan, open ticket ID : into a small JSON object injected into the system prompt. Far more token-efficient and far more reliable than hoping a summary preserved the right detail. This is the right answer for most task-oriented assistants.
  • Retrieval over history. Store past turns, embed them, and fetch only the ones relevant to the current message. This is RAG applied to conversation, and it is how long-lived assistants recall something from weeks ago. Covered in Parts 2 and 3.

Whichever you choose, count tokens before sending rather than discovering the limit through an error, and keep the system prompt outside whatever gets trimmed.

Part 2 : Embeddings and Vector Databases

Why embeddings matter

An embedding model converts text into a vector : a list of numbers, typically several hundred to a few thousand long : positioned so that semantically similar text lands close together. "How do I cancel my plan" and "ending your subscription" share almost no keywords but sit near each other in the space.

That property is what keyword search cannot give you. Lexical search matches strings; embedding search matches meaning, across synonyms, paraphrase, and often across languages. The applications follow directly: semantic search over documentation, clustering support tickets by theme, deduplicating near-identical catalogue entries, recommending related content, classifying by nearest labelled example, and : the dominant use : retrieving relevant passages to feed a generative model.

Three properties matter operationally. Embedding models are small, fast, and cheap relative to chat models, often by two orders of magnitude. Their output is fixed-length regardless of input length, which is what makes indexing tractable. And vectors from different models are mutually meaningless : change your embedding model and you must re-embed the entire corpus, so treat that choice as a migration, not a config flag.

How vector search works

Given a query vector, you want the stored vectors closest to it. Closeness is usually cosine similarity : the angle between vectors, which ignores magnitude : or dot product, which does not. Most embedding models are trained for one or the other; use what the model card specifies.

Comparing a query against every stored vector is exact but linear in corpus size, which stops being viable in the millions. Production systems therefore use approximate nearest neighbour search, trading a small amount of recall for a very large speedup. The dominant index is HNSW, a navigable small-world graph: vectors become nodes linked to their neighbours, arranged in layers, and a query descends from a coarse layer to progressively finer ones, following edges that reduce distance. Alternatives include IVF, which partitions the space into clusters and searches only the nearest few, and various quantization schemes that compress vectors to cut memory. HNSW is fast and accurate but memory-hungry : a practical planning figure is several gigabytes of RAM per million vectors at typical dimensions, so sizing matters before you scale.

Two refinements that separate a demo from a working system:

  • Metadata filtering. Real queries are rarely "find similar text" alone : they are "find similar text where tenant equals this customer and the document is not archived". Filter support, and specifically whether filtering happens before or during the graph traversal, varies significantly between engines and materially affects both correctness and latency.
  • Hybrid search. Pure vector search is weak precisely where keyword search is strong: exact identifiers, product codes, rare proper nouns, error strings. Hybrid search runs both lexical (BM25 or similar) and vector retrieval and fuses the rankings, commonly with reciprocal rank fusion. For most document corpora this is a larger quality improvement than any amount of prompt tuning, and it is the single most under-used lever in early RAG systems.

A reranking model is the usual final stage: retrieve twenty candidates cheaply, then score each against the query with a small cross-encoder that reads query and document together, and keep the best five. Slower per document, much more accurate, and applied to a short list it costs little.

Comparing Pinecone, Weaviate, and Chroma

These three are the most commonly evaluated stores, and they occupy genuinely different positions. Specific features move quickly, so weigh the shape of each rather than any feature checklist.

  • Pinecone is fully managed and proprietary, serving from the vendor's cloud with no infrastructure for you to run. Its serverless model removes capacity planning and scales with usage, and it carries the enterprise apparatus : compliance certifications, uptime commitments, and options for deployment into your own cloud account. Choose it when you want to ship product rather than operate a database, and accept that your vectors live with a vendor and pricing is theirs to set.
  • Weaviate is open-source with a managed cloud option, and its distinguishing strength is native hybrid search : vector, keyword, and metadata filtering as one query rather than something you assemble. It runs self-hosted, which matters when data cannot leave your boundary, and it suits enterprise workloads with complex filtering. The cost is operational: you are running a database.
  • Chroma is developer-first and local-first. It runs embedded in your process with no server at all, which makes it the fastest path from idea to working prototype, and its cloud offering has matured for lightweight production. Choose it for development, notebooks, and small-to-medium workloads; reassess when scale or multi-tenancy grows serious.

Two options outside the slide deserve mention because they are frequently the correct answer. pgvector adds vector search to PostgreSQL, so if you already run Postgres you may need no new system at all : a compelling position below roughly a hundred million vectors, and it keeps vectors transactionally consistent with the rows they describe. Qdrant is a fast Rust-based engine with a strong self-hosted story and good filtered-search performance, often chosen as an open alternative to Pinecone with a lighter operational footprint than Weaviate.

The honest guidance: at small scale all of these work, and retrieval quality is dominated by your chunking, your embedding model, and whether you use hybrid search : not by which engine stores the vectors. Prototype on Chroma or pgvector, and choose a production store based on your scale, your compliance constraints, and what your team can actually operate. Migration between them is real work but not exotic; over-engineering the choice on day one is the more common mistake.

Part 3 : Retrieval-Augmented Generation

The RAG pipeline explained

RAG grounds a model in your own documents without retraining anything. It has two phases, and conflating them is a common source of confusion.

Indexing, done ahead of time:

  1. Load. Pull documents from their sources : PDFs, wikis, ticket systems, databases. Extraction quality dominates everything downstream; a PDF parser that scrambles table columns guarantees bad answers no matter how good the rest of the pipeline is.
  2. Chunk. Split each document into passages sized for retrieval.
  3. Embed. Convert each chunk to a vector with your embedding model.
  4. Store. Write vectors plus the original text plus metadata (source, section, date, permissions) into your vector store.

Querying, at request time:

  1. Embed the query with the same model used for indexing.
  2. Retrieve the top candidates, applying metadata filters, ideally via hybrid search.
  3. Rerank the candidates and keep the best few.
  4. Assemble the prompt: system instructions, the retrieved passages clearly delimited and labelled with their sources, then the user's question.
  5. Generate, instructing the model to answer only from the supplied passages, to cite which passage each claim came from, and to say plainly when the passages do not contain the answer.

When a RAG system gives a bad answer, diagnose in that order. Print the retrieved chunks before blaming the model. In practice the overwhelming majority of RAG failures are retrieval failures : the right passage was never fetched : and no amount of prompt refinement fixes a passage that is not in the context.

Two upgrades worth knowing once the basic loop works. Query rewriting uses a cheap model call to turn a conversational follow-up ("what about the enterprise tier?") into a standalone search query, which matters enormously in multi-turn chat. And contextual retrieval prepends a short model-generated description of each chunk's place in its parent document before embedding it, which measurably reduces failures caused by chunks that are unintelligible in isolation.

Chunking strategies

Chunking is the highest-leverage and most neglected decision in the pipeline. Too large and a chunk contains mostly irrelevant text, diluting the embedding and wasting context. Too small and it loses the surrounding meaning that made it answerable.

  • Fixed-size with overlap. Split every N tokens with a 10–20% overlap so a sentence spanning a boundary appears whole in one of them. Crude, universal, and a reasonable baseline : roughly 300 to 800 tokens per chunk suits most prose.
  • Recursive character splitting. Split on the largest natural boundary that fits : paragraphs, then sentences, then words. Respects structure far better than fixed-size at essentially no extra cost. This should be your default.
  • Document-structure-aware. Split on the document's own skeleton: markdown headings, HTML sections, slide boundaries, function definitions in code. When your corpus has reliable structure, this is clearly best : and carrying the heading path into each chunk's text ("Billing > Refunds > Partial refunds") sharply improves retrieval.
  • Semantic chunking. Embed sentences and cut where consecutive sentences diverge in meaning. Elegant, sometimes better on unstructured prose, and meaningfully more expensive to build. Try it only after the simpler options are tuned.
  • Small-to-big (parent-document) retrieval. Embed and search over small precise chunks, but pass the larger parent section to the model. This resolves the central tension : small chunks retrieve accurately, large chunks answer completely : and is one of the highest-return patterns available.

Some content resists all of this. Tables should be kept intact with their headers repeated, since a table split mid-body becomes unreadable. Code should be split on function or class boundaries. Conversational transcripts often chunk best by speaker turn or topic shift rather than length.

There is no universally correct chunk size. Build an evaluation set of twenty real questions with known correct sources, then measure retrieval recall across two or three chunking configurations. An afternoon of that beats weeks of intuition.

Choosing embedding models

Judge candidates on five axes:

  • Retrieval quality on your data. Public benchmarks are a starting filter, not an answer : they are heavily optimized against and rarely resemble your domain. Take fifty real queries with known correct documents and measure recall at five and ten for each candidate model.
  • Dimensionality. Larger vectors capture more nuance and cost more in storage, memory, and query time. Several current models support truncating dimensions with graceful quality loss, letting you trade explicitly rather than choosing a model by size.
  • Maximum input length. Embedding models have their own token limits, often smaller than you expect. Text beyond the limit is truncated silently, which produces a subtly broken index rather than an error.
  • Domain and language fit. A general model handles general prose well and may do poorly on legal, clinical, or code corpora, or on languages underrepresented in its training. Multilingual models exist specifically for the last case.
  • Hosting and cost. Hosted APIs are simple and priced per token. Open-weight embedding models are small enough to self-host on modest hardware, which is often the decisive option when documents cannot leave your environment : and at high volume, cheaper.

One asymmetric consideration: switching embedding models means re-embedding and re-indexing everything. Weigh that against the cost of staying on a weaker model, and prefer models with a credible maintenance story over whichever one currently tops a leaderboard.

Part 4 : Evaluation of LLM Outputs

The habit that separates teams shipping reliable LLM features from teams shipping unpredictable ones is systematic evaluation. Reading two or three outputs and forming an impression feels like testing and is close to worthless, because output varies run to run.

Hallucination detection

Hallucination is confident, fluent, false output. In a grounded system there is a sharper and more tractable definition: a claim in the answer that the retrieved passages do not support. That version can be measured.

  • Groundedness checking. Decompose the answer into individual claims, then check each against the supplied context with a separate model call. The output is a proportion : what fraction of claims are supported : which you can track as a metric and alert on.
  • Citation enforcement. Require the model to attach a source identifier to each claim, then verify programmatically that every identifier exists and that the cited passage actually contains the assertion. Unverifiable citations become a visible failure instead of a silent one.
  • Self-consistency sampling. Generate the same answer several times at non-zero temperature. Facts the model actually retained stay stable; fabrications vary between runs. Effective, and costs several times the tokens.
  • Uncertainty signals. Where token log-probabilities are exposed, low confidence across a span correlates loosely with fabrication. A weak signal on its own, useful combined with others.
  • Structural prevention. Cheaper than detection: supply the source material, permit "I don't know" explicitly, lower the temperature, and keep the answer scoped to what was retrieved.

Note that a hallucination check is itself a model call and can be wrong. Treat these as instruments with known error bars, not oracles.

Automatic evaluation

Three generations of technique coexist, and knowing which is appropriate matters.

N-gram overlap metrics : BLEU and ROUGE. These predate LLMs. BLEU, from machine translation, measures how much of the generated text's word sequences appear in a reference translation. ROUGE, from summarization, measures the inverse : how much of the reference appears in the generated text : with variants for unigrams, bigrams, and longest common subsequence. Both are fast, deterministic, and free. Both are also blind to meaning: a perfect paraphrase using different words scores poorly, and a fluent nonsense answer reusing the reference's vocabulary scores well. They remain reasonable for tasks with tight reference outputs, such as translation or extraction, and are poor proxies for open-ended generation quality. Embedding-based metrics like BERTScore address the paraphrase problem partially by comparing meaning rather than exact tokens.

RAG-specific frameworks : RAGAS and its peers. These decompose a RAG system into components and score each, which is what makes them useful for debugging rather than just grading. The standard dimensions are faithfulness (is the answer supported by the retrieved context), answer relevancy (does it address the question asked), context precision (are the retrieved passages actually relevant), and context recall (did retrieval find everything needed). The last two isolate retrieval from generation, so a poor score tells you which half to fix. Many of these metrics are computed by model calls under the hood, so they cost tokens and carry the judge's own noise.

LLM-as-judge. A model scores output against explicit written criteria. This is now the workhorse for open-ended tasks because it is the only automatic method that handles "is this a good explanation for a non-technical reader". It works acceptably for coarse judgements and poorly for fine ones. Known biases are worth designing around: judges favour longer answers, favour text from the same model family, and are sensitive to option ordering in pairwise comparisons. Mitigate with an explicit rubric rather than "rate 1-10", pairwise comparison instead of absolute scoring, position randomization, and periodic calibration of the judge against human labels.

Alongside all of these, keep the cheap deterministic checks: does the output parse as valid JSON, does it match the schema, is it within length bounds, does it avoid a forbidden-terms list. These catch a surprising share of real failures at zero token cost.

Human-in-the-loop review

Automatic metrics tell you whether something changed. Humans tell you whether it is good. You need both, and the practical question is where to spend scarce human attention.

  • Build a golden set. Fifty to two hundred representative inputs with human-reviewed ideal outputs or explicit acceptance criteria, including the awkward edge cases. This is the asset your evaluation rests on; it is worth real effort and it should grow every time production surfaces a new failure mode.
  • Review by sampling, not exhaustively. Once live, sample a small percentage of traffic for human review, stratified so that low-confidence and unusual cases are over-represented rather than reviewing a random slice of easy successes.
  • Capture implicit signals. Thumbs up and down, copy events, edits users make to generated text, and abandonment all indicate quality at volumes no review panel can match. Edits are especially rich : the diff tells you exactly what was wrong.
  • Gate high-stakes output. Where a mistake is expensive : anything customer-facing, financial, medical, legal, or irreversible : a person approves before it takes effect. Design the review surface to make approval fast, showing the sources alongside the claim.
  • Close the loop. Every human correction is a future test case. Feed disagreements back into the golden set and into your judge's calibration.

Run the whole evaluation suite on every prompt change, model change, and retrieval change, and track scores over time. Regressions should be visible in a dashboard, not discovered by a customer.

Part 5 : Prompt Engineering Techniques

Structured output prompting

Prose is fine for humans; software needs parseable data. Getting reliable JSON out of a model has progressed through three stages, and you should use the strongest one your provider supports.

  • Prompt-only. Ask for JSON, supply an example, and parse what comes back. It mostly works and fails in irritating ways : a markdown code fence around the JSON, an explanatory sentence before it, a trailing comma, a hallucinated extra field.
  • JSON mode. A provider flag constraining the output to syntactically valid JSON. It guarantees parseability but not your shape : you still get valid JSON with wrong field names if the prompt is vague.
  • Schema-constrained generation. You supply a JSON Schema and the decoder is restricted at each step to tokens that keep the output conformant. This guarantees structure, including required fields, enums, and types. Where available it is strictly better, and it makes downstream parsing code straightforward rather than defensive.

Practical notes regardless of mechanism. Name fields descriptively, because field names are part of the prompt and refund_reason_category steers the model better than field3. Prefer flat schemas; deep nesting degrades reliability. Use enums to constrain classification rather than hoping for consistent free text. Provide an explicit representation for absence : null, or an "unknown" enum member : or the model will invent plausible values to fill required fields. And always validate after parsing: schema conformance does not mean semantic correctness.

Tools and function calling

Tool calling lets the model reach outside its own text. You describe available functions with a name, a description, and a parameter schema. The model, when it judges a call useful, returns a structured request naming the function and its arguments. Your code executes it : the model never does : and returns the result as a tool-result message. The model continues with that result in context.

The loop, concretely: send messages plus tool definitions; receive either a final answer or a tool-use request; if a request, execute it, append both the request and its result to the message list, and send again; repeat until the model answers.

This is the mechanism underneath essentially every genuinely useful LLM feature: live data lookups, database queries, exact arithmetic via a calculator or code interpreter, and actions in real systems. Design guidance that saves real debugging time:

  • The description is the prompt. Tool selection is driven almost entirely by name and description quality. Say what the tool does, when to use it, and when not to.
  • Keep the toolset small. Selection accuracy degrades as the count grows. Past roughly a dozen or two, group tools and expose only the relevant subset for the task at hand.
  • Return errors as text the model can act on. "No customer found with that ID; try searching by email" is useful. A raw stack trace is not.
  • Validate arguments before executing. The model produces plausible arguments, not guaranteed-valid ones. Never pass them into a query, a shell, or a filesystem path unchecked.
  • Separate read from write. Reads can run freely. Writes, payments, deletions, and sends should require confirmation, a policy check, or a human, because a model that can act can act wrongly.
  • Mind prompt injection. If a tool returns untrusted content : a web page, an email, an uploaded document : instructions hidden in it may be followed. Never let retrieved content authorize a privileged action.

The Model Context Protocol has emerged as a standard for exposing tools to models across vendors, which is worth knowing about if you are building tools that several applications will share.

Chain-of-thought prompting

Asking a model to reason step by step before answering improves accuracy on multi-step problems, because each intermediate step becomes context for the next. Compressing a hard problem into a single answer token gives the model no room to work.

Variants in ascending cost:

  • Zero-shot chain of thought. Append an instruction to work through it step by step. Nearly free, often effective.
  • Few-shot chain of thought. Provide worked examples that show the reasoning, not just the answers. The model imitates the reasoning style, which is the point.
  • Self-consistency. Sample several reasoning paths at moderate temperature and take the majority answer. A solid accuracy gain on arithmetic and logic, at several times the cost.
  • Decomposition. Break the problem into explicit sub-questions answered in sequence, each feeding the next. More controllable and more debuggable than one long chain, because you can inspect and test each stage.

Three cautions. Reasoning-tuned models do this internally and may perform worse when you also push hard on explicit chain-of-thought prompting : check the provider's guidance rather than assuming. Visible reasoning consumes output tokens, which is the expensive side of the bill, so keep it off simple tasks. And reasoning text is not a faithful audit trail: a model can produce sound-looking steps and a wrong answer, or the right answer through invalid steps. Useful for accuracy, not to be presented to users as an explanation of how the conclusion was reached.

When you need the reasoning without showing it, ask for the working inside a delimited block followed by the final answer in a separate field, and strip the block before display.

Part 6 : Building Agents

An agent is a model given a goal, a set of tools, and a loop in which it decides what to do next, observes the result, and continues until the task is done. The step up from a single tool call is autonomy : the model, not your code, chooses the sequence.

Tools, actions, and planning

Three components, each with its own failure modes.

Tools are the agent's capabilities, defined exactly as in Part 5. For agents specifically, granularity matters: a few well-designed composite tools outperform many fine-grained ones, because every additional step is another chance to go wrong. Tools should be idempotent where possible, since agents retry.

Actions are executions of those tools, and this is where agents stop being a prompt engineering exercise. An agent that can send email, modify records, or spend money needs boundaries that are enforced in your code rather than requested in the prompt: allowlists of permitted operations, spending and rate caps, hard step limits to stop runaway loops, dry-run modes, and approval gates on anything destructive or irreversible. Frameworks orchestrate behaviour; none of them enforces policy for you.

Planning is how the agent decides the sequence. Two broad approaches. Plan-then-execute has the model draft a full plan upfront and work through it : predictable, auditable, cheaper, and brittle when reality diverges from the plan. Interleaved planning decides the next step after each observation : adaptive, recovers from surprises, and prone to drift and loops. Hybrids are common: an upfront plan with explicit replanning when a step fails.

Also give the agent a way to finish. Define what done looks like, a hard cap on steps, and a path to escalate to a human. Agents that cannot recognize completion will keep going.

Agent frameworks

Frameworks supply the loop, state management, tool plumbing, and tracing you would otherwise build. The landscape consolidated noticeably through 2025 and 2026, so check current status rather than trusting older tutorials.

  • LangChain and LangGraph. LangChain remains the broadest integration ecosystem : model providers, vector stores, loaders, and evaluators : and is the most widely adopted by a wide margin. For agents specifically, LangGraph is now the recommended path within that ecosystem: it models the agent as an explicit state graph with cycles, giving durable state, checkpointing, and first-class human-in-the-loop interrupts instead of an opaque loop. LangSmith provides the tracing and evaluation layer. The trade-off is surface area; the abstractions are extensive and take time to learn well.
  • Semantic Kernel and Microsoft Agent Framework. Semantic Kernel was Microsoft's LLM orchestration SDK, notable for multi-language support and fitting .NET and Azure environments. It has since been consolidated with AutoGen into Microsoft Agent Framework, which reached general availability with graph-based workflows and Python and .NET runtimes. If you are on the Microsoft stack, that is now the path; Semantic Kernel documentation you find online may predate the consolidation.
  • LlamaIndex. Strongest where the agent is a knowledge worker over your data. Its document parsing, indexing, and retrieval primitives are its core investment, and its event-driven workflow layer handles document-heavy agentic pipelines. Choose it when retrieval quality over a large corpus is the hard part of your problem.

Two further notes. Model providers now ship their own lighter agent SDKs, and a visible strand of opinion holds that these plus the Model Context Protocol are displacing heavyweight frameworks for straightforward use cases : MCP in particular standardizes tool exposure across vendors, which removes a large part of what frameworks were needed for. And for a single-agent loop with three tools, no framework at all is a legitimate and often superior choice: the loop is about thirty lines, and you keep full visibility into what is happening. Reach for a framework when you need durable state, multi-agent coordination, checkpointing, or the tracing infrastructure.

Common agent patterns

  • ReAct (reason + act). The foundational pattern: the model alternates between a reasoning step and an action, observing each result before deciding the next move. Simple, general, and the basis of most agent implementations, whether or not they use the name. Its weakness is drift on long tasks : without periodic re-anchoring to the original goal, agents wander.
  • Autonomous goal-seeking loops. The AutoGPT-style pattern : give a high-level objective and let the system generate and pursue its own subtasks indefinitely : was enormously influential in demonstrating what agents could be, and proved unreliable in production. Long unsupervised loops accumulate errors, spiral in cost, and get stuck. The field has moved toward bounded, checkpointed, and supervised designs. Know the pattern; do not build on it unsupervised.
  • Plan-and-execute. Decompose into an explicit plan, then execute the steps, replanning on failure. More predictable and cheaper than open-ended looping, and much easier to audit.
  • Reflection. The agent critiques its own output against the goal and revises. A meaningful quality gain on writing and code, with diminishing returns after one or two rounds : and a separate critic instance with explicit criteria works better than asking a model to grade itself informally.
  • Multi-agent. Specialized agents with distinct roles and tools, coordinated by a supervisor or by handoffs. Genuinely useful when subtasks need different tools or contexts, and often just an expensive way to add latency and failure modes when a single agent would do. Try one agent first.
  • Human-in-the-loop checkpoints. The agent pauses at defined points for approval before proceeding. The most important production pattern on this list, and the one most often skipped.

Start narrow. A single agent, three tools, a tight scope, a step cap, and full tracing will teach you more than an ambitious multi-agent system that fails in ways you cannot diagnose.

Putting It Together

A realistic build order for an intermediate project, each step producing something that works:

  1. A single API call behind your own backend endpoint, with streaming, retries, and token logging.
  2. Multi-turn conversation with a sliding window, then structured state extraction when the window starts hurting.
  3. Embed a modest document set into Chroma or pgvector and build semantic search over it : no generation yet, just retrieval you can inspect.
  4. Wrap retrieval in a RAG loop with source citation and an explicit "not in the documents" path.
  5. Build a golden set of fifty questions with known sources. Measure retrieval recall. Fix chunking until it stops being the bottleneck.
  6. Add hybrid search and a reranker. Re-measure : this is usually the largest single quality jump.
  7. Add structured output and one tool call. Validate everything the model produces.
  8. Add an agent loop only when a task genuinely requires multiple dependent steps, with a step cap and tracing from the first run.

Instrument throughout: log every prompt, response, retrieved chunk, tool call, and token count. When something goes wrong in an LLM system, the trace is the only thing that tells you where.

Glossary

  • ANN : approximate nearest neighbour search; trades exactness for speed at scale.
  • HNSW : hierarchical navigable small world, the dominant graph-based vector index.
  • Hybrid search : combining keyword (BM25) and vector retrieval, fusing the rankings.
  • Reranker : a cross-encoder that rescores retrieved candidates against the query.
  • RAG : retrieval-augmented generation; retrieving passages and supplying them as context.
  • Chunking : splitting documents into retrieval-sized passages.
  • Small-to-big retrieval : searching over small chunks but passing the larger parent section to the model.
  • Query rewriting : converting a conversational follow-up into a standalone search query.
  • Groundedness / faithfulness : whether an answer's claims are supported by the retrieved context.
  • BLEU / ROUGE : n-gram overlap metrics from translation and summarization; meaning-blind.
  • RAGAS : a RAG evaluation framework scoring faithfulness, answer relevancy, context precision and recall.
  • LLM-as-judge : using a model to score output against written criteria.
  • Golden set : a curated set of inputs with known-good outputs, used as a regression suite.
  • JSON mode / schema-constrained generation : provider features forcing output to valid JSON or a supplied schema.
  • Function calling / tool use : the model requesting execution of a described function, with your code executing it.
  • MCP : Model Context Protocol, a standard for exposing tools to models across vendors.
  • Chain of thought : prompting the model to reason step by step before answering.
  • Self-consistency : sampling multiple reasoning paths and taking the majority answer.
  • ReAct : the reason-then-act agent loop.
  • Prompt injection : hidden instructions in untrusted input being followed by the model.

Frequently Asked Questions

Should I use the chat endpoint or the completions endpoint?

Use the chat endpoint for all new work. It matches how instruction-tuned models were trained and is the basis for tool calling, structured output, and multimodal input. Completions endpoints are deprecated or de-emphasized almost everywhere.

How do I give an LLM conversation memory?

Resend the conversation history with each request, since the model is stateless. Manage growth with a sliding window, periodic summarization, structured extraction of key facts into the system prompt, or retrieval over past turns for long-lived assistants.

Which vector database should I choose?

Pinecone for fully managed zero-ops production, Weaviate for native hybrid search and self-hosting, Chroma for local development and lightweight production. Consider pgvector if you already run PostgreSQL, or Qdrant for fast self-hosted deployment. Retrieval quality depends far more on chunking, embedding model, and hybrid search than on which engine you pick.

Why is my RAG system giving wrong answers?

Check retrieval before blaming the model. Print the chunks that were actually retrieved for the failing query. Most RAG failures are retrieval failures : the right passage was never fetched : and prompt changes cannot fix a passage that is absent from the context.

What chunk size should I use for RAG?

Start with recursive splitting on natural boundaries at roughly 300 to 800 tokens with 10–20% overlap, and split on document structure where reliable structure exists. Then measure retrieval recall on real questions across a few configurations, because there is no universally correct size.

Are BLEU and ROUGE useful for evaluating LLM output?

Only for tasks with tight reference outputs, such as translation or extraction. Both measure n-gram overlap and are blind to meaning, so a correct paraphrase scores poorly. For open-ended generation, use RAG-specific metrics, LLM-as-judge with an explicit rubric, or human review.

Is Semantic Kernel still current?

Semantic Kernel has been consolidated with AutoGen into Microsoft Agent Framework, which reached general availability with graph-based workflows and Python and .NET runtimes. For Microsoft-stack projects that is now the path, and older Semantic Kernel tutorials may predate the change.

Do I need an agent framework?

Not for a single-agent loop with a few tools : that is roughly thirty lines of code, and writing it yourself keeps full visibility. Reach for a framework when you need durable state, checkpointing, multi-agent coordination, or production tracing and evaluation infrastructure.

Why do autonomous agent loops fail in production?

Errors compound across steps, costs escalate quietly, and agents get stuck repeating actions or drift from the original goal. Bounded designs with step caps, explicit completion criteria, checkpointing, and human approval on consequential actions are substantially more reliable than open-ended autonomy.
