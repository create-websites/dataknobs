Overview

Six decisions shape the system

Agent architecture involves more than just selecting a framework. Its design begins with six key structural decisions: number of agents, distinction between planning and action, delegation structure, event handling model, orchestration runtime, and communication protocol.

1

Single vs. Multi-Agent

Decide whether to use a single shared reasoning loop or multiple specialized agents working together toward a shared objective.

2

Planner–Executor

Distinguish between choosing an action and executing it, allowing for re-planning if circumstances shift.

3

Supervisor–Worker

Employ a coordinator to direct tasks to expert workers, verify outputs, retry failures, and compile results.

4

Event-Driven Agents

Respond asynchronously to requests, webhooks, schedules, and various events instead of adhering to a predetermined synchronous sequence.

5

Orchestration Frameworks

Select the runtime that handles state, memory, routing, handoffs, retries, observability, and human intervention.

6

Communication Protocols

Establish uniform agent-to-tool communication and inter-agent delegation using open interfaces like MCP and A2A.

Decision 1

Start with one agent; earn the right to add more

A single-agent design involves one model, one context, and one reasoning loop managing its tools. In contrast, a multi-agent design distributes tasks among specialists. While having more agents can enhance parallelism and specialization, it also brings added coordination overhead and potential new points of failure.

Single-agent strengths

Simple and observable

  • Easier to build, debug, and trace.
  • No synchronization overhead across agents.
  • Lower token cost and usually lower latency.
  • More predictable behavior for bounded workflows.
Watch out

As tools and the range of tasks expand, context can become overloaded, and a single loop might have difficulty handling highly parallel or specialized tasks.

Multi-agent strengths

Specialized and parallel

  • Clear separation of concerns.
  • Independent subtasks can run in parallel.
  • Different roles can use different models or prompts.
  • Scales to broad, heterogeneous problem spaces.
Watch out

Routing, synchronization, retries, tracing, and cross-agent context transfer all evolve into architectural challenges.

A general guideline: begin with a single agent. Transition to multiple agents only if the task is truly parallel, requires different expertise, or cannot be neatly contained within a single context.
Decision 2

Planner–executor separates strategy from action

For lengthy tasks, allowing an agent to move straight from goal to action may lead to drift. Planner–executor frameworks incorporate a distinct planning stage prior to execution and enable the system to update the plan when tool outcomes, errors, or new data challenge initial assumptions.

Goal›Planner›Plan›Executor + tools›Result

How the pattern works

The planner breaks down the objective into a sequential task list. The executor carries out each step, invoking tools when needed. Progress is monitored against the plan, and setbacks or new information may prompt a re-planning. This intentionally separates strategic reasoning from the practical use of tools.

Variants in the source deck

Plan-and-Execute creates the plan first and executes it sequentially. ReWOO plans tool calls up front to reduce model round-trips. LLMCompiler depicts work as a task graph, allowing independent steps to execute concurrently.

Decision 3

Supervisor–worker creates a clear control hierarchy

A supervisor holds responsibility for the main objective, assigns specific tasks to specialized workers, verifies their outcomes, and combines them into the final result. This approach is common when various roles are necessary, yet a single point of accountability is required.

Strengths
  • Clear control and accountability.
  • Workers can remain narrow and expert.
  • Workers are easy to add, replace, or nest.
  • The supervisor can route, retry, and validate.
Failure modes
  • The supervisor can become a bottleneck.
  • It can become a single point of failure.
  • Poor routing quality caps overall system quality.
  • Too much context can accumulate at the top.

Hierarchies can also be recursive: an employee may take on the role of supervisor for a smaller subgroup. This makes the structure scalable, but every added layer raises the demands for observability and coordination.

Decision 4

Event-driven agents fit asynchronous and long-running work

An event-driven system substitutes a fixed request-response model with publish/subscribe interactions. Events are produced by requests, API webhooks, schedules, and timers; independent agents subscribe to these events and respond asynchronously.

Why it changes the architecture

Event-driven architectures reduce coupling between components. Producers are not required to identify the specific consumer of an event, and new subscribers can be added without modifying the producer. This facilitates easier horizontal scaling and parallel processing.

Best-fit workloads

  • Real-time alerts, monitoring, support, and reactive systems.
  • Long-running or human-in-the-loop workflows that wait on external events.
  • High-throughput pipelines with parallel, independent handlers.
The trade-off is operational: tracing distributed event flows is more difficult, ordering and eventual consistency require deliberate design, and implementing retry and dead-letter handling becomes crucial.
Decision 5

Orchestration frameworks operationalize the design

The framework serves as the runtime layer that transforms the selected architecture into a managed system. The deck categorizes orchestration into four types: graph-based, role-based, handoff-based, and hierarchical.

Decision 6

Protocols separate vertical tool access from horizontal agent collaboration

The deck frames agent communication in two directions: down to tools, data, and APIs, and across to other agents. Open protocols aim to standardize those boundaries.

MCPModel Context Protocol

Vertical integration between an agent and tools, data, or APIs through a client-server interface.

A2AAgent-to-Agent

Lateral communication for discovery, authentication, and delegation among agents and stacks.

ACPAgent Communication Protocol

A lightweight, REST-based method for agent messaging, outlined in the presentation as moving toward the A2A approach.

ANPAgent Network Protocol

A developing decentralized identity method focused on open agent networks and marketplaces.

Design principles

What to optimize for in production

In all six decisions, the architecture must reduce unnecessary coordination and clearly define state, control, recovery, and accountability.

Minimize moving parts

Choose the smallest architecture capable of handling the workload. Additional agents are not without cost.

Make control visible

Identify the goal owner, those authorized to delegate, and the location of the execution state.

Design failure paths

Retries, re-planning, dead-letter management, validation, and escalation ought to be addressed as architectural considerations.

Keep boundaries explicit

Differentiate tool invocation, agent handoff, asynchronous events, and shared state.

Instrument the runtime

Tracing is essential in multi-step and multi-agent systems to understand what occurred and the reasons behind it.

Scale by need

Incorporate parallelism, specialization, and hierarchy only when the workload demands it.

FAQ

Common architecture questions

Should every complex AI workflow use multiple agents?

No. The original deck clearly advises beginning with a single agent and adding multiple agents only when tasks are truly parallel, need different expertise, or surpass what one context can handle effectively.

When is planner–executor useful?

It is beneficial for lengthy, multi-stage tasks where straightforward actions often deviate. The re-planning cycle is crucial when setbacks or updated information may render the initial plan obsolete.

What is the main risk of supervisor–worker systems?

The supervisor may serve as both a bottleneck and a single point of failure, with the quality of its routing decisions limiting the overall system's performance.

Why use event-driven agents?

They are well-suited for reactive, asynchronous, long-duration, or high-throughput tasks where agents need to react to events independently instead of following a fixed, blocking script.

What does an orchestration framework provide?

The deck emphasizes state and memory, control flow and routing, handoffs, retries and error recovery, tracing and observability, as well as human-in-the-loop support.

How do MCP and A2A differ in this model?

MCP serves as the vertical interface connecting agents with tools and data, whereas A2A functions as the horizontal interface enabling communication and delegation among agents.
