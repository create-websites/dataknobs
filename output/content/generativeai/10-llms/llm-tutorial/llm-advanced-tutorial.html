Detailed explanation

The content below expands on the slides with structured HTML article content.

Intermediate material gets a system working. This tutorial is about the gap between working and production : the part where latency budgets, unit economics, telemetry, schema guarantees, and failure recovery decide whether a feature survives contact with real traffic. It covers five areas: hardening a RAG system for scale, fine-tuning and customizing models, evaluating and monitoring live applications, building extraction pipelines that produce trustworthy structured data, and assembling multimodal applications from OCR, vision, and voice components. It assumes you have built a working RAG prototype and understand tool calling, chunking, and evaluation basics.

Part 1 : Building Production-Ready RAG

A RAG demo and a production RAG system differ less in architecture than in everything surrounding it: how documents get in and stay current, what the pipeline costs per query, and how much of that work can be avoided entirely.

Indexing large document sets

At a thousand documents, indexing is a script. At ten million chunks it is a pipeline with its own operational surface, and the decisions below are expensive to reverse.

  • Make ingestion incremental. Full re-indexing stops scaling almost immediately. Hash each source document's content and store the hash alongside its chunks; on each run, re-process only what changed and delete chunks belonging to removed documents. Without deletion handling, your index slowly fills with answers to questions about material that no longer exists.
  • Treat extraction as the quality ceiling. Everything downstream inherits the parser's mistakes. Scanned PDFs need OCR, multi-column layouts need reading-order reconstruction, and tables need structure-preserving extraction rather than flattened text. Budget real effort here: it typically has a larger effect on answer quality than any model choice in the stack.
  • Carry metadata from the start. Source, title, section path, author, timestamp, language, and : critically : access control identifiers. Retrofitting permissions onto an index that lacks them means a full rebuild, and a retrieval system that returns documents a user is not entitled to see is a data breach with extra steps. Filter by permission at query time, in the vector store, not after retrieval.
  • Batch and parallelize embedding. Embedding APIs accept batches; per-item calls waste most of the available throughput. Run a bounded worker pool, respect rate limits with backoff, and checkpoint progress so a failure at 80% does not restart from zero. For very large corpora, self-hosting a small embedding model on a GPU is often far cheaper than an API.
  • Separate the write path from the read path. Bulk index builds compete with query traffic for memory and CPU. Build into a new index or namespace, verify it, then switch reads over atomically. This also gives you a rollback when a re-index degrades quality.
  • Plan memory before you need it. Graph indexes such as HNSW hold vectors in RAM, and at typical dimensions a few million vectors is already tens of gigabytes. Quantization and dimension truncation trade a little recall for large memory savings; measure the recall cost on your own queries rather than accepting a vendor's benchmark.
  • Isolate tenants deliberately. Multi-tenant systems need either per-tenant namespaces or a hard metadata filter applied server-side on every query. Relying on application code to remember the filter is a leak waiting for its first bug.

Version your index alongside the configuration that produced it : embedding model, chunking parameters, extraction version. When quality regresses, the first question is what changed in the pipeline, and without versioning that question has no answer.

Latency and cost optimization

Start by measuring where the time and money actually go. A typical RAG request decomposes into query embedding, vector search, reranking, prompt assembly, and generation. Generation usually dominates both budgets, but not always : an unoptimized reranker over fifty candidates, or a synchronous chain of model calls for query rewriting, can quietly become the bottleneck.

Latency levers, roughly in order of return:

  • Stream the response. Time to first token is what users experience as speed. A streamed answer beginning in 400ms feels faster than a complete one delivered in 2s, even though the latter finished sooner.
  • Parallelize independent work. Query embedding, metadata lookups, and permission checks can run concurrently. Anything not on the critical path should not be on the critical path.
  • Shrink the rerank pool. Reranking is a cross-encoder pass per candidate. Retrieve fifty and rerank fifty and you have bought accuracy with latency; retrieving twenty and reranking twenty is usually indistinguishable in quality.
  • Cut context length. Prefill time scales with input tokens. Passing eight passages when three suffice costs latency on every request and often reduces answer quality through dilution.
  • Route by difficulty. Send simple classification and routing decisions to a small fast model; reserve the frontier model for the generation that actually needs it. This is simultaneously the largest latency and cost lever available.
  • Cap output length. Generation is sequential, so output tokens translate almost linearly into wall-clock time. An instruction to answer in under 150 words is a latency optimization.
  • Move work off the request path. Query rewriting, summarization of history, and safety scoring can often run asynchronously, speculatively, or on the previous turn.

Cost levers overlap heavily. Model routing dominates. Beyond it: trim fixed prompt overhead, since a long system prompt and five few-shot examples are billed on every request forever; constrain output, which is the expensive side of the ledger; batch non-interactive work through a provider's batch API where available, often at a substantial discount; and self-host the small, high-volume components : embedding and reranking especially : where unit economics favour it.

Instrument cost per request, not just aggregate spend. Cost per resolved ticket or per document processed is the number that tells you whether the feature is economically viable; a monthly total tells you only that it is expensive.

Caching strategies

The cheapest model call is the one you do not make. Four distinct caches operate at different layers, and mature systems use all of them.

  • Exact-match response cache. Hash the fully assembled prompt and store the response. Trivially correct, zero risk of semantic drift, and effective wherever traffic repeats : FAQ-style queries, retries, and automated callers. Key on everything that affects output, including model identifier, temperature, and retrieved context, or you will serve responses generated under different conditions.
  • Semantic cache. Embed the incoming query and return a cached answer when an earlier query is close enough. This catches paraphrase, which exact matching misses entirely, and it introduces a genuine correctness risk: "how do I upgrade my plan" and "how do I downgrade my plan" are semantically adjacent and have opposite answers. Set the similarity threshold conservatively, scope caches per tenant and per permission set, and never apply semantic caching to queries whose answers depend on time or user state.
  • Prompt (prefix) caching. Providers cache the processed prefix of a prompt, so a large fixed system prompt, tool definitions, or a stable document reused across requests is billed and computed at a steep discount on subsequent calls. This is often the single highest-return optimization available and requires only that you structure prompts with the stable content first and the variable content last. Cache entries expire after minutes, so it rewards steady traffic.
  • Component caches. Embeddings for unchanged text, retrieval results for repeated queries, reranker scores for a query-document pair, and parsed document structures are all deterministic given their inputs and worth caching independently of the generation layer.

Invalidation is where caches turn into bugs. Tie cache keys to the versions of everything upstream : index version, prompt version, model identifier : so that a deployment invalidates naturally rather than serving yesterday's answers from today's system. Track hit rate as a first-class metric: a cache nobody measures is a cache nobody knows has stopped working.

Part 2 : Fine-Tuning and Customizing Models

Before anything in this section: fine-tuning is the third thing to try, not the first. Prompt engineering is free and immediate. RAG handles knowledge, which changes. Fine-tuning handles behaviour : consistent format, domain tone, a classification boundary the model keeps getting wrong, or compressing a long elaborate prompt into a small fast model. Fine-tuning to teach facts is the classic expensive mistake: the facts go stale, the model states them confidently anyway, and you cannot update them without retraining.

Prompt-based fine-tuning and instruction tuning

Supervised fine-tuning takes a base or instruct model and trains it further on your own prompt-and-completion pairs. The model learns to produce your kind of output for your kind of input. Format the training data exactly as production requests will arrive : same system prompt, same message structure, same delimiters : because a mismatch between training and serving format is the most common cause of a fine-tune that performs worse than the model it started from.

What fine-tuning reliably buys you:

  • Format adherence without a long instruction block, so output shape becomes a property of the model rather than something re-negotiated each request.
  • Domain voice and conventions that are tedious to specify and easy to demonstrate.
  • Cost and latency collapse : a small tuned model matching a large prompted one on a narrow task, often at a fraction of the price. This is frequently the real business case.
  • Edge-case behaviour that prompting keeps failing on, taught by example instead of by rule.

Beyond supervised tuning, preference tuning methods such as DPO train on pairs of better and worse responses rather than single correct answers. They suit subjective qualities : helpfulness, tone, refusal behaviour : where you can more easily say which of two outputs is better than write the ideal one. They need preference data, which is a heavier collection effort.

Always hold out a test set before training, and always compare against a well-engineered prompt on the base model. A fine-tune that does not beat a good prompt is a maintenance burden you have chosen to take on.

LoRA and QLoRA

Full fine-tuning updates every parameter, which requires memory for the weights, their gradients, and optimizer state : in practice many times the model's own size, putting it out of reach for most teams on anything but small models.

LoRA (low-rank adaptation) sidesteps this. It freezes the original weights and injects small trainable matrices alongside selected layers, exploiting the observation that the weight update needed for adaptation has low intrinsic rank. Typically well under 1% of parameters are trained. The consequences are practical:

  • Memory requirements fall dramatically, bringing meaningful models within reach of a single GPU.
  • The resulting adapter is small : megabytes, not gigabytes : so you can store many, and serve multiple adapters against one shared base model, swapping per request. This makes per-customer or per-task customization economically sane.
  • Adapters can be merged into the base weights for deployment when you prefer a single artifact with no inference overhead.

Two hyperparameters matter most: the rank, which sets adapter capacity (low ranks suffice for style and format; raise it for genuinely new behaviour), and the scaling factor, commonly set to a small multiple of the rank. Which layers receive adapters also matters : attention projections are the usual target, and extending to the feed-forward layers helps on harder adaptations at some extra cost.

QLoRA goes further by quantizing the frozen base model to 4-bit precision while training the adapters in higher precision, with the base dequantized on the fly during computation. Memory drops far enough that models which would otherwise demand a multi-GPU node fit on a single consumer or workstation card. The costs are modest but real: training is slower because of dequantization overhead, and quality sits very close to LoRA but not always identically. For most teams QLoRA is what makes fine-tuning possible at all, and the right default when hardware is the binding constraint.

Operationally, remember that serving a quantized base with an adapter is a different deployment from serving merged full-precision weights, and evaluate the configuration you will actually ship rather than the one you trained on.

Dataset creation best practices

Dataset quality dominates every other choice in fine-tuning. A thousand carefully constructed examples routinely beat fifty thousand scraped ones.

  • Start smaller than you think. For format and style adaptation, a few hundred to a few thousand high-quality examples is often sufficient. Build a small set, train, evaluate, and let the measured gap tell you whether more data is the answer : frequently the answer is better data, not more.
  • Match production distribution. Your training inputs should look like real traffic, including the messy, ambiguous, and adversarial cases. A dataset of clean examples produces a model that is confident and wrong on everything else.
  • Enforce consistency ruthlessly. Inconsistent labels or formats teach inconsistency, and the model will reproduce your dataset's contradictions faithfully. Write an explicit annotation guideline, and measure agreement between annotators before scaling up.
  • Balance and deduplicate. Over-represented classes bias output. Near-duplicate examples inflate the count without adding signal and encourage memorization.
  • Use synthetic data carefully. Generating training data with a stronger model is legitimate and widespread : and unreviewed synthetic data bakes the generator's errors and quirks into your model permanently. Human-review a meaningful sample, filter aggressively, and check the provider's terms regarding training on outputs.
  • Include negative and refusal examples. If the model should decline, ask for clarification, or return a null result, that behaviour must appear in the data. Otherwise it will confidently answer everything.
  • Split before you touch anything. Hold out a test set at the start, keep it untouched, and check for leakage between splits. Near-duplicates spanning train and test produce excellent metrics and a disappointing deployment.
  • Version datasets like code. Record which dataset version produced which model, with the changes between them. Without that lineage, a regression is unattributable.

Finally, plan for drift. Production language, product vocabulary, and user behaviour move. A fine-tune is a snapshot, so schedule periodic re-evaluation against fresh production samples rather than assuming a model tuned last quarter still fits this quarter's traffic.

Part 3 : Evaluating and Monitoring LLM Apps

Offline evaluation tells you whether a change is safe to ship. Monitoring tells you what is happening to real users right now. Production LLM systems need both, and the second is the one teams usually skip.

Logging, telemetry, and observability

LLM applications break traditional monitoring assumptions. The same input produces different outputs, so you cannot reproduce an incident without having captured the exact input, model, and parameters at the time. Cost and latency track token counts rather than request counts. And a request is rarely one call : it is a chain of retrieval, reranking, tool calls, and generation, any link of which can be the fault.

Trace, don't just log. Model the whole request as a distributed trace: a parent span for the request, child spans for each retrieval, rerank, tool call, and model invocation, nested to reflect actual structure. For agents, the span tree is the reasoning chain, and it is the only practical way to answer "why did it do that".

The ecosystem has been converging on a standard here. OpenTelemetry's GenAI special interest group has defined semantic conventions for generative AI : standard gen_ai.* attribute names covering model, token usage, finish reason, tool calls, and agent steps : so telemetry works across backends without custom parsing. Coverage has expanded from LLM client calls to agent orchestration, tool calling, content capture, and quality evaluation. Much of it remains experimental, and attribute names have shifted between versions, so pin your instrumentation version and use the stability opt-in mechanism when migrating. Auto-instrumentation exists for the major SDKs and frameworks, which is the fastest path to useful traces.

What to capture per request: model identifier and version, all generation parameters, input and output token counts, computed cost, latency broken down by stage, finish reason, retrieved chunk identifiers and scores, tool calls with arguments and results, prompt template version, cache hit or miss, error class on failure, and a correlation identifier tying it to your application's user session.

Handle content carefully. Prompts and completions routinely contain personal or confidential data, and storing full prompt text in indexed span attributes is an anti-pattern : attributes have size limits and expose content throughout your observability backend. The conventions put content in span events instead, which can be filtered or dropped at the collector without touching application code. Redact before export, sample content capture rather than storing everything, and set retention deliberately.

Alert on the things that actually indicate trouble: error and timeout rates, p95 latency by stage, cost per request trending upward, token usage anomalies, cache hit rate collapse, retrieval returning zero or low-scoring results, schema validation failure rate, and refusal or fallback rate. A dashboard nobody looks at is not monitoring; thresholds with owners are.

The tooling landscape includes open platforms such as Langfuse, Arize Phoenix, MLflow's tracing layer, and OpenLLMetry, alongside vendor offerings like LangSmith and Helicone, and general APM vendors that now ingest GenAI conventions. Prefer whatever emits and consumes the open conventions, so your traces remain portable.

Safety filters

Safety in production is layered, and no single layer is sufficient.

  • Input filtering. Screen incoming text for policy-violating content, and detect prompt injection attempts : particularly in any input that originated from a document, a web page, or an email rather than being typed by the user. Classify rather than pattern-match; regex lists are trivially evaded.
  • PII handling. Detect and redact personal data before it reaches the model or your logs, or tokenize it and restore values after generation. Decide this before launch, because retrofitting redaction across a telemetry backend already full of personal data is painful.
  • Output filtering. Screen generated text before it reaches the user for policy violations, leaked system-prompt content, leaked credentials, and claims outside the retrieved context. Output filtering is the last gate before a mistake becomes visible.
  • Grounding checks. In RAG systems, score whether the answer is supported by the retrieved passages, and degrade gracefully : withhold, caveat, or escalate : when it is not.
  • Action gating. For anything that writes, sends, spends, or deletes, enforce policy in your own code: allowlists, rate and spend caps, and explicit approval for consequential or irreversible operations. Frameworks orchestrate behaviour; they do not evaluate a tool call against policy before it executes. That layer is yours to build.
  • Topic and scope constraints. A support assistant answering questions about geopolitics is a reputational risk with no upside. Constrain scope explicitly and handle out-of-scope requests with a defined response.

Every filter has false positives, so log blocks with enough context to review them, give users a path when they are wrongly blocked, and treat filter thresholds as tunable parameters with their own evaluation set. Red-team before launch: have people actively try to break the system, and keep their successful attacks as regression tests.

A/B testing prompts

Offline evaluation on a golden set is necessary and insufficient : it measures what you thought to measure on inputs you chose. Online experimentation measures what real users do.

  • Version prompts as artifacts. Prompts belong in version control or a prompt registry with identifiers, not embedded as string literals across the codebase. Every trace should record which version produced it, or your experiment has no readable results.
  • Randomize at the right unit. Assign by user or session, not by request. A user flipping between two prompt variants mid-conversation gets an incoherent experience and pollutes your data.
  • Pick a primary metric before launching. Task completion, resolution without escalation, edit distance between generated and sent text, explicit thumbs, or downstream conversion. Choose one, and keep guardrail metrics alongside it : latency, cost per request, error rate, safety-filter trigger rate : so you notice when a quality win was purchased with a cost or latency regression.
  • Respect statistics. LLM output metrics are noisy. Compute the sample size you need beforehand, resist stopping the moment results look good, and use sequential testing methods if you genuinely need to peek. Most disappointing "wins" are early-stopping artifacts.
  • Change one thing. A variant that alters the prompt, the model, and the retrieval depth together tells you only that something changed.
  • Keep rollback instant. Prompt and model selection should be runtime configuration, not a deployment. When a variant misbehaves at 2am, the fix should be a flag flip.

Also run shadow evaluations: send a sample of production traffic to a candidate configuration without showing users the result, score both offline, and compare. It gives you real-distribution evidence at zero user risk, which is especially valuable for model upgrades.

Part 4 : JSON Extraction Pipelines

Extraction is where LLMs deliver the most unglamorous value: turning invoices, emails, contracts, forms, and support threads into structured records. It is also where "mostly right" is not good enough, because the output feeds systems that expect valid data.

Parsing structured data from messy inputs

Real inputs are inconsistent in ways rule-based parsers handle badly: fifty vendors' invoice layouts, dates in every regional format, amounts with varying currency conventions, scanned pages with OCR noise, multilingual documents, and fields that are sometimes absent and sometimes implied.

A workable pipeline stages the problem rather than asking one model call to do everything:

  1. Normalize the input. Convert to text with layout preserved where it carries meaning. For PDFs, keep reading order and table structure; for HTML, strip chrome but retain headings and table markup. Poor normalization is the most common root cause of extraction failure, and it is invisible unless you look at the intermediate text.
  2. Segment before extracting. Long documents extract better when split into regions : header, line items, totals, terms : and processed separately. It shortens context, sharpens the instruction, and makes failures localized rather than total.
  3. Extract with a schema. One model call per region with an explicit output schema, as described next.
  4. Normalize the output. Dates to ISO format, amounts to decimal with an explicit currency code, identifiers trimmed and case-normalized, enums mapped to your canonical values. Do this in code, deterministically, rather than asking the model to be consistent about it.
  5. Attach provenance. For each extracted field, record where it came from : page, region, or the verbatim source span. This makes human review fast and disputes resolvable, and it is the single most useful thing you can add to an extraction system.

Design for absence explicitly. Give every field a defined representation for "not present in the document", and instruct the model to use it. Without that, required fields get filled with plausible inventions : the most dangerous failure mode in extraction, because it is silent and well-formatted.

Enforcing schemas

Asking politely for JSON is not a guarantee, and defensive parsing of free-form output is a maintenance sink. Use the strongest available mechanism:

  • Schema-constrained decoding. You supply a JSON Schema and the decoder is restricted at each step to tokens that keep the output conformant. Structure becomes a hard guarantee rather than a hope : required fields present, types correct, enums respected. Where a provider or serving stack supports it, this is strictly the right choice, and open-weight serving stacks offer equivalent grammar-constrained generation.
  • JSON mode. Guarantees syntactic validity but not your shape. Better than nothing; still needs schema validation after parsing.
  • Prompt-only. The fallback. Expect code fences, preambles, and trailing commas, and write a tolerant extraction step around the parse.

Schema design has a large effect on accuracy, because the schema is part of the prompt:

  • Name fields descriptively and use the description properties : invoice_total_including_tax with a one-line description outperforms total.
  • Prefer flat structures; deeply nested objects degrade reliability noticeably.
  • Use enums wherever the value space is closed, which converts a generation problem into a classification problem.
  • Keep types strict and simple : strings for identifiers that may have leading zeros, explicit decimal strings for money if your consumers are picky about floats.
  • Include a confidence or evidence field per extracted value when you plan to route low-confidence records to review.

Validate after parsing regardless. Conformance to a schema says nothing about semantic correctness: dates can be structurally valid and impossible, line items can sum to something other than the stated total, and identifiers can be well-formed and nonexistent.

Correction loops and validation

A production extraction pipeline is not one model call; it is an attempt followed by checks followed by targeted repair.

  • Layer the checks. Schema validation first, then type and format validation, then business rules (line items sum to the total, dates fall in plausible ranges, the tax rate matches the jurisdiction), then cross-referencing against systems of record (does this vendor exist, does this purchase order number resolve).
  • Repair narrowly. When validation fails, send the model the original input, its previous output, and the specific error : not a generic "try again". A targeted message ("line_items total 4,820.00 but invoice_total is 4,280.00; re-check the line items") resolves most recoverable failures in one retry.
  • Bound the loop. Two retries, then escalate. Models that fail twice on the same input rarely succeed on the fifth attempt, and unbounded correction loops are a cost incident waiting to happen.
  • Escalate with context. A failed record should reach a human with the source document, the extracted values, the validation errors, and the provenance spans : so review takes seconds rather than a full re-read.
  • Use consensus where stakes justify it. Extract twice, ideally with different prompts or models, and compare. Agreement is a strong correctness signal; disagreement routes straight to review. It roughly doubles cost and is usually worth it on financially consequential fields only.
  • Close the loop with corrections. Every human fix is a labelled example. Accumulate them into an evaluation set, and eventually into fine-tuning data for a smaller, cheaper extraction model.

Track field-level accuracy, not document-level. "94% of documents correct" hides which field fails and why; per-field precision and recall tells you exactly where to spend effort, and usually reveals that one or two fields account for most of the error.

Part 5 : Building Multi-Model AI Apps

Sophisticated applications stop being one model behind one prompt. They become pipelines where specialized components : OCR, vision, speech, embedding, generation : each do what they are best at, coordinated by your code.

The OCR to JSON to LLM pipeline

The canonical document-processing architecture has three stages, each with a clear contract:

  1. OCR / document understanding. Convert the image or scanned PDF into text with layout : words, their positions, reading order, table structure. Modern document-AI services return structured layout rather than a flat string, and that structure is worth preserving because it disambiguates which number belongs to which label.
  2. Structured extraction. An LLM call with a schema turns that layout-aware text into validated JSON, with the correction loop from Part 4 around it.
  3. Reasoning and action. Downstream, a model or ordinary business logic consumes the structured record : summarizing, comparing against policy, routing for approval, writing to a system of record.

The value of the separation is that each stage is independently testable, cacheable, and replaceable. OCR output caches permanently for a given document. Extraction can be re-run with an improved schema without re-OCRing. And you can measure accuracy at each boundary, which is what makes the pipeline debuggable : when the final answer is wrong, you can tell whether the text was wrong, the extraction was wrong, or the reasoning was wrong.

Vision models for extraction

Multimodal models that accept images directly offer an alternative: skip explicit OCR and hand the page to the model. Each approach wins in different places.

Vision-direct is stronger on visually complex documents where layout carries meaning : forms with checkboxes, documents where position determines which label a value belongs to, charts, screenshots, handwriting, and anything where a linearized text dump loses the plot. It is simpler to build, with fewer moving parts.

OCR-first is stronger on dense text where accuracy per character matters, is typically cheaper at volume, produces text you can index and search independently, and gives you character-level confidence scores that vision models generally do not expose. It is also more auditable.

A hybrid is frequently best: OCR for the text layer, the page image supplied alongside it, and the model given both. Practical cautions for the vision path : images consume input tokens, often a lot, and resolution drives that count, so downscale deliberately and check how your provider tokenizes images. Split multi-page documents rather than sending twenty pages at once. And verify extracted numbers rather than trusting them: vision models read dense tables and small print less reliably than they read prose, and a misread digit in a financial field is a serious error delivered with total confidence.

Audio and voice interfaces

Voice applications follow one of two architectures, and the choice is mostly about latency versus control.

The cascaded pipeline runs speech-to-text, then the LLM, then text-to-speech. Each stage is separately swappable, testable, and loggable; you get a transcript for free, which matters for compliance and evaluation; and you can apply text-domain safety filters between stages. The cost is accumulated latency, and information loss : tone, emotion, and emphasis vanish at the first stage.

The speech-native approach uses models that accept audio and emit audio directly, preserving prosody and cutting latency substantially. It gives up the intermediate transcript and much of the stage-level control, though most such APIs can emit transcripts alongside audio.

What actually determines whether a voice interface feels good:

  • Latency budget. Conversational turn-taking tolerates only a few hundred milliseconds of silence before it feels broken. Stream everything, start speaking before generation completes, and measure time-to-first-audio, not total response time.
  • Turn detection. Knowing when the user has finished speaking, rather than merely paused, is the difference between a natural exchange and constant interruption. Voice activity detection plus a semantic endpointing check works better than a silence timer alone.
  • Barge-in. Users interrupt. Stop playback immediately, and truncate the conversation history to what was actually heard, not what was generated : otherwise the model believes it said things the user never received.
  • Transcription errors propagate. Names, addresses, and identifiers are the common failures. Confirm critical values explicitly, and bias recognition toward your known vocabulary where the API supports it.
  • Write for the ear. Prompts must instruct shorter sentences, no markdown, no bulleted lists, and spelled-out numbers where clarity demands it. Text that reads well is often unbearable to listen to.

Voice also raises consent and retention questions that text does not. Recording rules vary by jurisdiction, so decide early what audio you keep, for how long, and with what disclosure.

Orchestrating multiple models

Beyond modality, mature applications route across models deliberately. A small fast model classifies intent and decides where a request goes. An embedding model retrieves. A reranker orders. A mid-tier model handles the bulk of generation. A frontier model handles the minority of genuinely hard cases. A separate judge model scores a sample of output for quality.

Build this behind an internal abstraction so that model selection is configuration rather than code, with a defined fallback when a provider degrades and per-stage cost and latency tracked independently. The gains are substantial : typically most of the quality at a fraction of the cost : and so is the added failure surface, so add stages only when measurement shows they earn their place.

Production Readiness Checklist

  1. Ingestion is incremental, handles deletions, and carries permissions into the index.
  2. Index builds happen out of band with an atomic switchover and a rollback path.
  3. Latency and cost are measured per stage and per request, not just in aggregate.
  4. Prefix caching is in use, prompts are ordered stable-first, and cache hit rate is monitored.
  5. Model routing sends easy work to cheap models and hard work to capable ones.
  6. Every request emits a trace with standard attributes; content is redacted and retained deliberately.
  7. Input, output, and action-level safety layers exist, with red-team findings as regression tests.
  8. Prompts are versioned artifacts, experiments randomize by user, and rollback is a config change.
  9. Structured output is schema-constrained, validated semantically, and repaired in a bounded loop.
  10. Human escalation paths exist with full context, and corrections feed back into the evaluation set.
  11. Fine-tunes, if any, beat a well-engineered prompt on a held-out test set and are re-evaluated on a schedule.

Glossary

  • Incremental indexing : re-processing only changed documents, including deletions.
  • Prefix / prompt caching : provider-side reuse of a processed prompt prefix at reduced cost and latency.
  • Semantic cache : returning a cached answer when a new query is embedding-similar to an earlier one.
  • Model routing : directing requests to different models by difficulty or task type.
  • SFT : supervised fine-tuning on prompt-and-completion pairs.
  • DPO : direct preference optimization; training on better/worse response pairs.
  • LoRA : low-rank adaptation; training small injected matrices with base weights frozen.
  • QLoRA : LoRA over a 4-bit quantized base model, cutting memory further.
  • Rank : the capacity parameter of a LoRA adapter.
  • Adapter merging : folding a trained adapter into base weights for deployment.
  • Span / trace : the unit and tree of distributed telemetry for one request.
  • GenAI semantic conventions : OpenTelemetry's standard gen_ai.* attributes for LLM telemetry.
  • Shadow evaluation : running a candidate configuration on real traffic without showing users the result.
  • Guardrail metric : a metric watched during an experiment to catch regressions outside the primary goal.
  • Schema-constrained decoding : restricting generation so output conforms to a supplied schema.
  • Provenance : the recorded source location of each extracted value.
  • Correction loop : bounded re-prompting with specific validation errors after a failed extraction.
  • Cascaded voice pipeline : speech-to-text, then LLM, then text-to-speech as separate stages.
  • Barge-in : a user interrupting playback mid-response.
  • Endpointing : detecting that a speaker has finished their turn.

Frequently Asked Questions

How do I keep a large RAG index up to date?

Make ingestion incremental: hash source documents, re-process only what changed, and explicitly delete chunks for removed documents. Build into a new index or namespace and switch reads atomically so you can verify before cutover and roll back afterward.

What is the cheapest way to cut LLM costs in production?

Model routing usually wins : send simple work to a small model and reserve the frontier model for hard cases. After that, provider prefix caching with prompts structured stable-content-first, trimming fixed prompt overhead, and capping output length, which is the expensive side of the bill.

When should I fine-tune instead of using RAG?

Fine-tune for behaviour : consistent format, domain tone, a classification boundary, or compressing a long prompt into a small fast model. Use RAG for knowledge, which changes and needs to be updatable. Fine-tuning to teach facts produces a model that states stale information confidently.

What is the difference between LoRA and QLoRA?

LoRA freezes the base model and trains small injected matrices, cutting memory enormously versus full fine-tuning. QLoRA additionally quantizes the frozen base to 4-bit, cutting memory further so larger models fit on a single GPU, at the cost of slower training and a small quality risk.

How much data do I need to fine-tune a model?

Far less than most people expect for format and style adaptation : often a few hundred to a few thousand high-quality, consistently formatted examples. Quality and distribution match matter more than volume; a thousand curated examples routinely beat fifty thousand scraped ones.

What should I log for an LLM application?

Trace the whole request with spans for retrieval, reranking, tool calls, and generation. Capture model and parameters, token counts, computed cost, per-stage latency, finish reason, retrieved chunk IDs and scores, prompt version, and cache status. Redact content before export and keep prompts out of indexed span attributes.

How do I A/B test prompts safely?

Version prompts as artifacts recorded in every trace, randomize by user or session rather than per request, fix a primary metric plus guardrail metrics for cost, latency, and safety beforehand, size the sample properly, and keep model and prompt selection as runtime configuration so rollback is instant.

How do I guarantee valid JSON from an LLM?

Use schema-constrained decoding where available, which restricts generation to tokens that keep output conformant. JSON mode guarantees syntax but not your shape. In all cases, validate semantically after parsing : structurally valid output can still be business-logic wrong.

Should I use OCR or a vision model for document extraction?

Vision-direct suits visually complex documents where layout carries meaning : forms, checkboxes, charts, handwriting. OCR-first suits dense text, costs less at volume, yields searchable text and confidence scores, and is more auditable. A hybrid that supplies both OCR text and the page image is often best.

What makes a voice interface feel natural?

Latency above all : stream and measure time-to-first-audio. Then reliable turn detection so the system knows when the user finished rather than merely paused, immediate barge-in handling with history truncated to what was actually heard, and prompts written for the ear: short sentences, no markdown, no lists.
