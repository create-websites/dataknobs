The Data Lifecycle in High-Dimensional Space

A comprehensive, engine-by-engine look at Create, Read, Update, and Delete (CRUD) operations in vector databases : and the architectural tradeoffs behind each one.

Architectural Imperatives: The Primacy of the Read Path

Vector database architecture is overwhelmingly optimized for one primary function: the rapid retrieval of semantically similar vectors from a massive dataset.

The Challenge of Exact Search

A brute-force k-Nearest Neighbors (kNN) search, which compares a query vector to every other vector, is computationally infeasible at scale. The linear complexity, O(n), makes it too slow for real-time applications involving millions or billions of items.

The Solution: Approximate Nearest Neighbor (ANN) Search

Vector databases use specialized indexing structures to enable Approximate Nearest Neighbor (ANN) search. This approach trades a small, often negligible, amount of accuracy (recall) for an exponential gain in search speed, making real-time semantic search possible.

The HNSW Index: The Industry Standard

The Hierarchical Navigable Small World (HNSW) algorithm has become the de facto standard for ANN indexing. It organizes vectors into a multi-layered proximity graph where nodes are vectors and edges represent similarity. A search starts at the top "expressway" layer and greedily navigates closer to the query, descending to denser layers to refine the search. This intricate structure is the key to its speed but also the source of its resistance to modification.

A Deep Dive into Vector DB CRUD Operations

Create: The Ingestion and Indexing Pipeline

The Create operation is a multi-stage process involving two key steps: Vectorization, where raw data is converted into a vector embedding by a machine learning model, and Indexing, where the vector and its metadata are stored and added to the ANN index.

Many databases use an upsert operation, which combines "update" and "insert." If a vector's ID exists, it's updated; if not, it's created. For optimal throughput, it's crucial to batch these operations, sending hundreds or thousands of vectors in a single request.

Batched ingestion, in practice

def ingest(records, embed_model, index, batch_size=200):
    for batch in chunked(records, batch_size):
        vectors = embed_model.encode(
            [r.text for r in batch]
        )
        index.upsert([
            {"id": r.id, "values": v, "metadata": r.meta}
            for r, v in zip(batch, vectors)
        ])

Hybrid search: vector + metadata filter

results = index.query(
    vector=embed_model.encode(
        "wireless headphones under $100"
    ),
    filter={
        "category": {"$eq": "electronics"},
        "price": {"$lt": 100}
    },
    top_k=10
)

Read: Similarity Search and Hybrid Filtering

The Read operation is the core function of a vector database. It begins by vectorizing the user's query with the same embedding model used for the stored data. The database then performs an ANN search to find the "closest" vectors based on a chosen distance metric like Cosine Similarity or Euclidean Distance.

The true power lies in hybrid search, which combines this semantic search with structured metadata filtering, allowing for highly specific and contextually relevant queries (e.g., "find similar products where price < $100"). How the filter and the ANN search are actually combined under the hood is a bigger deal than it looks : see Pre-Filtering vs. Post-Filtering below.

Update & Delete: The High Cost of Mutability

Direct, in-place updates of vectors are rare and computationally expensive. Instead, an Update is almost always implemented as a logical "delete-then-insert" operation.

Similarly, a Delete is typically a "soft delete" or "tombstoning". The vector is not physically removed but is marked for deletion. This creates "holes" in the HNSW graph, degrading index navigability and performance over time. The actual removal happens during later maintenance processes.

Tombstones still cost graph traversal

for candidate in hnsw_search(query_vector, ef=64):
    if candidate.id in tombstones:
        continue  # skipped, but still traversed
    results.append(candidate)
    if len(results) == top_k:
        break

Every tombstoned node the graph walks through is wasted traversal : the more soft-deletes accumulate, the more this loop pays for candidates it will throw away.

Tuning HNSW for Production

HNSW exposes three parameters that trade recall, latency, memory, and build time against each other. Getting them wrong is invisible in a demo and expensive in production.

M

Max connections per node in the graph. Higher M improves recall and query speed but grows the index's memory footprint roughly linearly. Typical range: 16–64.

efConstruction

Search width used while building the graph. Higher values produce a better-connected, higher-quality graph at the cost of slower ingestion. Set once, felt at write time.

ef / efSearch

Search width at query time. The one knob you can safely change per-request without rebuilding anything : raise it for a high-stakes query, lower it for a cheap one.

Setting build-time and query-time parameters separately

# Build-time: paid once, when the collection is created
client.create_collection(
    collection_name="products",
    vectors_config=VectorParams(size=768, distance=Distance.COSINE),
    hnsw_config=HnswConfigDiff(m=32, ef_construct=200)
)

# Query-time: paid per request, tune per use case
client.search(
    collection_name="products",
    query_vector=query_embedding,
    search_params=SearchParams(hnsw_ef=128),
    limit=10
)

None of these have a universally "correct" value : the right setting depends on your recall target, query volume, and latency budget, which is exactly the kind of tradeoff worth measuring against your own data rather than copying a blog post's defaults.

Pre-Filtering vs. Post-Filtering

Combining a metadata filter with an ANN search sounds simple. How an engine actually does it changes your recall in ways that only show up once your filters get selective.

Post-Filtering

Run the ANN search first, then discard results that fail the metadata filter. Simple and fast to implement : but if the filter is narrow (say, 1% of the corpus matches), the ANN search can return a full page of candidates that all get filtered away, leaving you with too few results, or none.

Symptom in production: result counts that quietly shrink as filters get more specific, with no error to explain why.

Pre-Filtering

Restrict the candidate set to matching metadata before or during graph traversal : for example, only following HNSW edges into nodes that pass a bitmap filter. Correct results even under narrow filters, but it's more engineering to build well and can slow traversal when the filter excludes most of the graph.

Symptom in production: slower queries as filters get more selective, instead of fewer results.

Engines differ meaningfully on which strategy they use and how well it's implemented : this is a concrete, measurable thing to benchmark against your own filter patterns before picking an engine, not something to assume from the marketing page.

Maintaining a Healthy Index

To counteract the performance degradation caused by data churn, vector databases rely on crucial background maintenance processes.

Compaction

Compaction is the process of tidying up the index. It physically purges soft-deleted vectors, reclaiming storage space and removing query-time filtering overhead. It also merges small data fragments into larger, more efficient ones.

Re-indexing

Re-indexing involves rebuilding all or part of the ANN index to ensure it is optimally structured based on the current data. This process restores query latency and recall to peak levels but can be computationally expensive and time-consuming.

These asynchronous processes mean vector databases operate on an eventual consistency model. There is an inherent delay between when a change is made and when it is fully reflected across the optimized index.

Consistency & Durability Under the Hood

Eventual consistency doesn't mean "unsafe" : it describes a specific, well-understood durability pattern.

Write-Ahead Logging

Most production vector databases layer a write-ahead log (WAL) underneath the ANN index: a write is durably logged before it's applied to the in-memory graph. If the process crashes mid-update, the log replays on restart : the same durability pattern relational databases have used for decades, applied here to a much less mutation-friendly data structure.

Replication Lag Is the Real "Eventual" in Eventual Consistency

In a replicated deployment, a write acknowledged by the primary hasn't necessarily reached every replica yet. A read routed to a lagging replica can miss a just-written vector, or still return one that was just deleted. If your application logic assumes read-after-write consistency, verify it : don't assume it.

Maintenance Runs on Top of, Not Instead of, the WAL

Compaction and re-indexing (above) are optimizations layered on a durability model that's already keeping your data safe. Turning them off doesn't threaten durability : it just lets tombstones and fragmentation accumulate until query latency and recall degrade.

Practical Implementations: Code Examples

The same four CRUD operations, across six engines with genuinely different APIs.

Pinecone


# Assumes 'index' is an initialized Pinecone index object
# Create/Update
index.upsert(
    vectors=[{"id": "vec1", "values": [0.1, ..., 0.9], "metadata": {"genre": "fiction"}}],
    namespace="example-namespace"
)
# Read (Similarity Search)
query_results = index.query(vector=[0.1, ..., 0.9], top_k=5, filter={"genre": {"$eq": "fiction"}})
# Delete
index.delete(ids=["vec1"], namespace="example-namespace")

pgvector (PostgreSQL)


-- Create
INSERT INTO items (id, embedding, metadata)
VALUES (1, '[0.1, 0.2, ..., 0.9]', '{"genre": "fiction"}');
-- Read (Similarity Search)
SELECT id, metadata FROM items
ORDER BY embedding <=> '[0.1, 0.2, ..., 0.9]'
LIMIT 5;
-- Update
UPDATE items SET embedding = '[0.2, ...]' WHERE id = 1;
-- Delete
DELETE FROM items WHERE id = 1;
