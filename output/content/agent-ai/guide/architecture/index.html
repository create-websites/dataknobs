Use archetypes as architecture patterns, not product categories

Modern agents increasingly combine multiple patterns. The value of an archetype is to clarify dominant tools, failure modes and controls.

01 · Knowledge

Agentic retrieval / research

Plans searches, retrieves across sources, compares evidence and produces citation-backed synthesis.

02 · Code

Coding / sandbox agent

Inspects files, edits code, runs commands and tests changes inside a controlled execution environment.

03 · GUI

Computer-use agent

Operates interfaces through visual/semantic computer controls when dedicated APIs are absent or incomplete.

04 · Workflow

Business process agent

Coordinates APIs and enterprise systems to complete a bounded workflow such as support, finance or operations.

05 · Network

Multi-agent orchestrator

Delegates to specialists or remote agents, often using explicit handoffs or A2A across organizational boundaries.

What changed from older “CodeAct vs RAG vs CUA” taxonomies

CodeAct remains a useful action pattern, but executable code is now better treated as one implementation strategy inside a broader coding/sandbox archetype. Likewise, agentic RAG is increasingly part of research and knowledge workflows rather than a standalone endpoint architecture. The 2026 view emphasizes execution boundary and control profile.

Frequently asked questions

Are these archetypes mutually exclusive?

No. A production system may combine research, coding, computer use and multi-agent orchestration. The taxonomy helps identify dominant action surfaces and control needs.

Is CodeAct still an archetype?

It is better treated as an action implementation pattern: using generated code as an expressive tool interface: inside coding or general tool-using agents.
