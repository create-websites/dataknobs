Decision rules for orchestration

01

Prefer one agent when possible

A single well-scoped agent is easier to evaluate, secure and operate. Add specialists when the boundary creates measurable value.

02

Use handoffs for ownership changes

A handoff should transfer a bounded task, context and allowed authority: not an entire conversation and credential set by default.

03

Use tools for deterministic capabilities

Calculators, rules, database reads, transaction services and validators should remain explicit tools rather than being reimplemented as probabilistic reasoning.

04

Use parallelism selectively

Parallelize independent research or analysis, but serialize steps that depend on shared state, approval, ordering or transaction integrity.

05

Make memory intentional

Separate task state from durable memory. Durable writes should have provenance, retention and review rules.

06

Treat remote agents as third parties

Authenticate peers, validate capabilities and outputs, constrain delegated authority and retain evidence for cross-agent calls.

MCP and A2A in the architecture

MCP

  • Connects agent applications to tools, resources and context providers
  • 2026 specification adds stateless core and authorization hardening
  • Useful for capability discovery and standardized tool access
  • Requires the same inventory, identity, authorization and supply-chain controls as other integrations

A2A

  • Enables interoperable communication and collaboration between agents
  • Now an open Linux Foundation project
  • Useful when agents span vendors, frameworks or organizational boundaries
  • Peer trust, delegation and identity must be explicit; interoperability is not authorization

Autonomy maturity model

1 · Assist

Agent researches or drafts; human executes.

2 · Recommend

Agent proposes a plan or action with evidence.

3 · Execute with gates

Agent executes approved low/medium-risk actions; high-risk actions require review.

4 · Bounded autonomy

Agent runs recurring workflows inside explicit policies, budgets and exception handling.

Frequently asked questions

What should a supervisor agent own?

Planning, delegation, state coordination and synthesis. It should not automatically inherit every specialist’s credentials or bypass policy controls.

How do you prevent a multi-agent system from becoming a privilege-escalation path?

Use per-agent identities and scopes, capability-specific tokens, policy checks on each handoff, provenance on peer messages, bounded delegation depth and independent authorization at the action boundary.

Do multi-agent systems always outperform a single agent?

No. They add coordination cost, latency and failure modes. Use multiple agents only when specialization, isolation, parallelism or organizational boundaries provide measurable benefit.
