A2A in one sentence

Current statusThe official A2A specification lists v0.3.0 as the latest version, and in August 2026 the project joined the Agentic AI Foundation as a Growth Stage project.

Agent2Agent (A2A) is an open protocol for communication between independent AI agent systems. Its purpose is interoperability: an agent can discover another agent’s capabilities, negotiate how to exchange information, and manage collaborative tasks without needing direct access to the other agent’s internal memory, tools or implementation.

Latest spec: v0.3.0Open interoperability protocolAAIF Growth Stage, Aug 2026

The core protocol objects

Discovery

Agent Card

Describes identity, endpoint, capabilities, supported interfaces and security expectations so another system can decide whether and how to collaborate.

Work

Task

Represents collaborative work and its lifecycle. Long-running work can progress through states rather than being reduced to one request/response.

Exchange

Messages + Artifacts

Messages carry conversational or structured inputs; artifacts represent outputs produced as work progresses or completes.

Compatibility

Modalities

Agents can negotiate text, files and structured data rather than assuming every participant shares the same internal representation.

A2A and MCP solve different boundaries

MCP: agent ↔ tools and context

MCP is primarily the vertical integration layer that connects an AI application to tools, resources and data. Its July 2026 specification moved to a stateless core and strengthened authorization.

A2A: agent ↔ independent agent

A2A is the horizontal collaboration layer for peer systems that may be built by different teams or vendors and should not expose their private internals to each other.

Design rule: protocol interoperability does not remove authorization. Treat peer agents as external principals with authenticated identity, explicit scopes, task-level policy, data minimization and auditable handoffs.

Enterprise architecture decisions

Discovery trustDo not treat every published Agent Card as trusted. Maintain approved registries or validate provenance and ownership before delegation.
IdentityMap the remote agent to an authenticated nonhuman principal and preserve the human/application sponsor that initiated the work.
Data minimizationSend only task-relevant context; redact or tokenize sensitive data before cross-boundary handoffs.
Task authorityConstrain what the peer can request back and what downstream actions its artifacts can trigger.
ObservabilityRecord task IDs, agent identities, messages, artifact hashes, policy decisions, errors, latency and downstream use.
Failure handlingDefine timeouts, cancellation, retries, idempotency and compensation for partial multi-agent workflows.

Frequently asked questions

What is the most important enterprise control for A2A?

Treat every remote agent as a separate security principal. Authenticate it, authorize the task, minimize shared context and retain auditable evidence of the handoff and returned artifacts.

Can an A2A peer be trusted because it advertises a capability?

No. Capability discovery is not trust. Organizations still need provenance, allowlists or registries, identity, policy, validation and monitoring.
