LLM Tutorial for Beginners: Learn LLM Basics

Article

Detailed explanation

The content below expands on the slides with structured HTML article content.

Large language models have gone from research curiosity to everyday tool in a remarkably short span, and the gap between casually using one and actually understanding it is where most beginners get stuck. This tutorial closes that gap. It covers four foundations in order: what an LLM is and how it works, how to prompt one properly, how tokens and context windows govern both quality and cost, and how to tell the available types of model apart. No machine learning background is assumed.

Part 1 : What Is an LLM?

A large language model is a program that has learned the statistical structure of human language by reading an enormous quantity of text. Underneath every chat interface and every API is a single narrow skill: given a stretch of text, predict what is most likely to come next.

That one skill generalizes further than it has any right to. Predicting the next word in a legal contract requires absorbing something about contracts. Continuing a Python function correctly requires absorbing something about Python. Finishing "the capital of Japan is" requires having retained a fact. Because language is the medium in which humans record nearly everything they know, a system that models language well ends up modelling a great deal of the world as a side effect.

The word "large" is carrying weight. These models hold billions of adjustable numbers, called parameters, and are trained on text measured in trillions of words. Language models are decades old; what changed recently was scale, an architecture that scales efficiently, and hardware capable of training at that size. Abilities nobody explicitly programmed : translation, summarization, working code, coherent conversation : emerged as the models grew.

The rest of this section opens the box at a high level: how text becomes tokens, how tokens become meaning, and how the transformer architecture turns that into a prediction.

Step one: tokenization

A model never sees letters or words. Input text is first chopped into tokens : chunks sitting between a character and a word. "Hello" is usually a single token. "Tokenization" splits into three or four. An unusual name or a technical term can fragment into many. Spaces and punctuation typically attach to neighbouring tokens.

Each distinct token maps to an ID number in a fixed vocabulary, often 50,000 to 200,000 entries. So the first thing that happens to your prompt is conversion into a list of integers. Everything downstream operates on those integers, never on your original characters.

This explains a class of failure that otherwise looks baffling. Ask a model how many times the letter "r" appears in a word and it may get it wrong : it never saw the letters, only two or three opaque chunks. Character-level puzzles, precise spelling manipulation, and arithmetic on long digit strings are all harder than they appear for exactly this reason. Part 3 returns to tokens in depth, because they also govern limits and cost.

Step two: embeddings

Token IDs are arbitrary : the number assigned to "cat" tells you nothing about cats. So each token ID is converted into a list of numbers called a vector, or an embedding, often several thousand numbers long. These values are learned during training rather than assigned by hand.

The property that makes embeddings valuable is that geometric closeness corresponds to semantic closeness. The vectors for "physician" and "doctor" land near each other. "Paris" sits near "London" and "Tokyo" along one axis and near "France" along another. Relationships become consistent directions through the space, which is why the well-known arithmetic : king minus man plus woman arrives near queen : works at all.

Embeddings are not purely an internal detail. They are sold as a product in their own right and power semantic search, clustering, deduplication, and recommendation. Part 4 covers embedding models as a distinct category.

Step three: the transformer

Nearly every modern LLM is built on the transformer architecture, introduced in a 2017 research paper. You do not need the mathematics to use these systems well, but the core idea is intuitive and explains a lot of behaviour.

The central mechanism is attention. As the model processes each token, it looks across the other tokens present and decides how much weight to give each when interpreting the current position. Take the sentence: "The trophy did not fit in the suitcase because it was too large." To resolve "it", the model must attend strongly to "trophy" rather than "suitcase". Swap "large" for "small" and the correct target flips. That context-dependent resolution is what attention buys, and it is why transformers handle long-range dependencies far better than what came before.

A transformer stacks this operation dozens of times. Each layer refines every token's representation using information drawn from all the others, and layers tend to specialize : earlier ones on surface structure, later ones on abstract relationships. Crucially, attention across the input runs in parallel rather than strictly word by word, which is what made training at today's scale economically feasible.

After the final layer, the model produces a probability score for every token in its vocabulary, representing how likely each is to come next. One token is selected, appended to the text, and the whole process repeats. This is why responses stream in rather than appearing at once : you are watching the loop run.

How a model is trained

Three stages, each doing something different:

  • Pretraining. The model is shown vast quantities of text and repeatedly asked to predict the next token, with its parameters nudged whenever it guesses wrong. This consumes the overwhelming majority of the compute and produces a model that is knowledgeable but unhelpful : ask it a question and it may well continue with more questions.
  • Instruction tuning. Further training on curated instruction-and-response pairs teaches the model the format of being useful: when given a request, answer it. This converts a text-continuation engine into an assistant.
  • Preference training. Human reviewers compare candidate outputs and mark which they prefer; those judgements steer the model toward responses people find more helpful, accurate, and safe. Reinforcement learning from human feedback, or RLHF, is the best-known method.

Two consequences follow directly. Every model has a training cutoff, a date beyond which it has seen nothing : it will not know about later events and may state outdated information confidently. And the model's tone and sense of a good answer are not neutral properties of language; they result from choices made during tuning.

What an LLM is not

It is not a database and holds no lookup table of facts. It has no internet access unless the surrounding system provides a search tool. It retains no memory of you between sessions unless a developer built one. And it does not know things the way a person does : it produces text that is statistically plausible given what it absorbed. Usually plausible and true coincide. When they diverge you get hallucination: fluent, confident, well-formatted content that is simply false. Invented citations, non-existent software functions, and plausible-but-wrong dates are all common. Verify anything involving numbers, dates, quotes, or references, and treat the model's confident tone as carrying no evidential weight at all : it reads identically whether the content is solid or fabricated.

Part 2 : Prompting Basics

Prompting is simply writing input that reliably produces the output you want. It is less mystical than commonly presented, and a handful of techniques account for most of the achievable gain.

Role prompts vs. system prompts

Chat APIs do not take one undifferentiated block of text. They take a sequence of messages, each tagged with a role:

  • System. Sets persistent behaviour, identity, constraints, and output rules. It applies across the whole conversation and generally carries more weight than instructions buried in a user turn.
  • User. Carries the actual request and any material to work on.
  • Assistant. Holds the model's previous replies. You send these back on each turn, which is how a conversation maintains continuity : the model is stateless and reconstructs context purely from the messages you supply.

The practical rule: anything durable belongs in the system message, anything specific to this request belongs in the user message. If you are building a support assistant, "You are a support assistant for an accounting product. Never speculate about pricing. If you do not know, say so and offer to escalate." goes in the system prompt once, not appended to every user question.

A common beginner confusion is worth naming. "Role prompting" also refers to the technique of assigning the model a persona : "You are an experienced technical editor." That is a content choice, usually placed inside the system message. The system message is the channel; the persona is one thing you might put in it. Persona framing helps most when it genuinely narrows the space of good answers (an editor knows what to cut) and helps least when it is decorative (calling the model a world-class genius changes little).

Prompt structure best practices

A prompt that works reliably usually contains most of these elements, roughly in this order: the task, the context or source material, the constraints, the output format, and then any examples.

  • State the task specifically. "Summarize this" leaves length, audience, and emphasis to chance. "Summarize this in five bullet points for a non-technical executive, focusing on cost implications" removes the guesswork.
  • Name the audience and the format. Who reads this, how long should it be, what shape should it take : bullets, a table, JSON, prose.
  • Say what to exclude. Negative constraints are as useful as positive ones: no preamble, no caveats, no marketing language, do not mention the source document.
  • Separate instructions from data. When you paste in a document, delimit it clearly with headers or tags so the model does not confuse content with commands. This also reduces the risk that instructions hidden inside untrusted text get followed.
  • Put instructions at the edges. Models use material at the very start and very end of a long input more reliably than material buried in the middle. Place critical rules there.
  • Ask for reasoning on hard problems. For multi-step work, having the model reason through the steps before answering improves accuracy, because each step becomes context for the next. Newer reasoning models do this internally and need less prompting for it.
  • Give the model an out. Explicitly permitting "I don't know" or "the source does not contain this" measurably reduces invented content. Without that permission, the pull toward a plausible-looking answer is strong.
  • Iterate. Treat the first prompt as a draft. Find where the output misses, add a constraint addressing that specific miss, run again. For anything heading to production, keep a small set of test inputs and check changes against all of them : a tweak that fixes one case routinely breaks another.

Zero-shot, one-shot, and few-shot prompting

These three terms describe how many worked examples you include in the prompt. The "shots" are demonstrations, and supplying them is sometimes called in-context learning : the model adapts from the examples without any change to its parameters.

  • Zero-shot. Instructions only, no examples. "Classify the sentiment of this review as positive, negative, or neutral." Fast, cheap, and usually sufficient for tasks the model already understands well.
  • One-shot. A single demonstration. Useful when the task is clear but the exact format is not: show one input with its ideal output, and the model copies the shape.
  • Few-shot. Typically two to five demonstrations. This is the most reliable technique available for pinning down structure, tone, edge-case handling, and labelling conventions. Three good examples beat three paragraphs describing the format.

Some practical guidance on examples. Make them representative of real inputs, including at least one awkward or ambiguous case, since that is where the model needs the most steering. Keep the formatting of every example rigorously identical : inconsistency teaches inconsistency. Balance the classes if you are classifying, because a set of examples that is mostly "positive" biases the output toward positive. And remember that examples consume input tokens on every single request, so there is a real cost trade-off: start zero-shot, add examples only where output quality actually demands it.

Part 3 : Tokens, Context Windows, and Costs

What tokens are

Part 1 introduced tokens as the unit a model reads. Here is what you need operationally.

A useful estimate for English is that one token is about four characters, or roughly three-quarters of a word. A thousand words of English prose lands near 1,300 tokens. That ratio degrades for other content: code tokenizes less efficiently because of punctuation and indentation, non-Latin scripts often need several tokens per character, and text dense with unusual proper nouns fragments heavily. If your workload is code or non-English, assume meaningfully more tokens per unit of content than the English rule of thumb suggests.

Both directions count. Input tokens cover your system prompt, conversation history, pasted documents, and few-shot examples. Output tokens cover what the model generates. They are counted separately and priced differently.

Every major provider publishes a tokenizer you can run on your own text. Ten minutes pasting real prompts into one is the fastest way to build intuition for what your application will cost.

How token limits impact responses

The context window is the total number of tokens the model can consider at once : system prompt, conversation so far, attached documents, and the response being generated, all counted together. Contemporary models range from tens of thousands of tokens to over a million.

The context window is the model's entire working memory. Anything outside it does not exist. This produces several effects you will meet in practice:

  • Conversations forget. When a long chat exceeds the limit, earlier turns must be dropped or summarized. This is why an assistant can appear to lose track of something you said an hour ago : it is not in the window any more.
  • Long documents get truncated. Paste in more than fits and the tail is silently cut. Answers about the missing portion will be confidently wrong.
  • Output gets cut off mid-sentence. There is usually a separate maximum output tokens setting, often much smaller than the context window. Hitting it truncates the response abruptly : a very common source of confusing bug reports.
  • Middles get neglected. Models do not attend equally across a long input. Material at the beginning and the end is used more reliably than material in the middle, an effect usually described as "lost in the middle". Position matters, not just inclusion.
  • Everything slows down. Attention compares tokens against each other, so work grows faster than linearly with input length. Long contexts mean slower responses.

The implication is that a bigger window is not automatically better. Supplying the right few thousand tokens generally outperforms supplying everything you have. When your material genuinely exceeds what fits, the standard answer is retrieval: index your documents, fetch only the passages relevant to the current question, and pass just those. That pattern is called retrieval-augmented generation, or RAG, and it is the usual next topic after these fundamentals.

Cost estimation basics

Commercial APIs price per million tokens, with input and output billed at different rates : output is typically several times more expensive, because generating tokens costs more compute than reading them. The arithmetic is straightforward:

cost per request = (input tokens ÷ 1,000,000 × input rate) + (output tokens ÷ 1,000,000 × output rate)

Work a concrete example. Suppose a support-summarization feature sends a 400-token system prompt, three few-shot examples totalling 900 tokens, and a 700-token ticket, then generates a 300-token summary. That is 2,000 input tokens and 300 output tokens per request. At an illustrative $3 per million input and $15 per million output, one request costs $0.006 of input plus $0.0045 of output, roughly $0.0105 : about a cent. Ten thousand tickets a month lands near $105.

The structure of that calculation matters more than the specific rates, which change frequently. Notice that the few-shot examples are 45% of the input, paid on every single request forever. Notice that 300 output tokens cost nearly as much as 2,000 input tokens. Those two observations drive most real cost optimization:

  • Trim the fixed overhead. Long system prompts and generous example sets are charged on every call. Cutting three examples to one, if quality holds, removes a third of your input bill.
  • Constrain output length. Asking for five bullets instead of an open-ended summary saves on the expensive side of the ledger.
  • Watch conversation growth. Every turn resends the whole history, so a long chat gets progressively more expensive. Summarize or truncate older turns.
  • Route by difficulty. The spread between a provider's small model and its frontier model is often an order of magnitude. Sending simple classification to the cheap model and reserving the expensive one for hard reasoning is the single highest-leverage optimization available.
  • Check for prompt caching. Most providers now offer a discount on repeated prefixes, which is substantial when a large fixed system prompt precedes a small variable input.
  • Set hard limits before you need them. Runaway loops and oversized contexts produce expensive surprises. Spending caps and per-request token limits are cheap insurance.

Part 4 : Model Types

"LLM" is used loosely to cover several distinct categories of model that do different jobs. Knowing which is which prevents a lot of wasted effort.

Chat models vs. embedding models

These are the two you will use most, and they are not interchangeable.

A chat model : also called a generative or completion model : takes messages and produces text. It writes, summarizes, answers, classifies, codes, and reasons. It is what people mean colloquially by "an LLM". It is comparatively large, comparatively slow, and priced per token in both directions.

An embedding model takes text and produces a vector of numbers : the representation described in Part 1. It generates no text at all. Its output is only useful in comparison to other vectors: how close is this question to that paragraph. Embedding models are small, fast, and dramatically cheaper, often by two orders of magnitude, and are typically priced on input only.

Choose by the question you are asking. If the answer is text a person will read, you need a chat model. If the answer is "which of these items is most similar", you need an embedding model. Semantic search, clustering support tickets by theme, deduplicating a catalogue, and retrieving relevant passages for a RAG pipeline are all embedding tasks. A common architecture uses both: an embedding model finds the relevant documents, then a chat model writes the answer from them. Two further notes : embeddings must be generated by the same model on both sides of a comparison, since vectors from different models are not comparable, and storing them at scale requires a vector index or a database extension that supports one.

You will also encounter reranking models, a narrower category that scores how well a document answers a query and is used to refine embedding search results, and reasoning models, chat models tuned to spend extra tokens working through a problem before answering : more accurate on hard analytical tasks, slower and more expensive on easy ones.

Open-weight vs. proprietary models

The other major division is how you get access.

Proprietary models are reached through a hosted API. The provider runs the infrastructure; you send requests and pay per token. You get frontier capability with no operational work, immediate access to improvements, and an uptime commitment. You give up control: your data leaves your environment, the model can change or be deprecated underneath you, pricing is not yours to set, and you are exposed to rate limits and outages.

Open-weight models publish their trained parameters for download. You can run them on your own hardware or through a hosting provider of your choice. You get data residency : input never leaves your boundary, which can be decisive under regulatory constraints : plus version stability, freedom to fine-tune, and potentially much lower unit cost at high volume. You take on GPU provisioning, serving infrastructure, scaling, and evaluation.

A note on terminology: "open-weight" and "open-source" are not synonyms. Most publicly released models publish weights without publishing training data or full training code, and many carry licences with usage restrictions. Read the licence before building a business on one.

A reasonable default for beginners is to prototype against a hosted API, since it removes every infrastructure question from the learning curve, then evaluate open-weight options once you know your actual volume, latency needs, and data constraints. Many mature systems run both : a hosted frontier model for the hard tenth of traffic and a self-hosted smaller model for the routine remainder.

Multimodal LLMs

Early language models handled text alone. Multimodal models accept, and sometimes produce, more than one kind of input : most commonly images alongside text, increasingly audio and video too.

The underlying trick is consistent with Part 1: other modalities are converted into the same kind of vector representation the model already uses for text, so an image becomes a sequence of embeddings the transformer can attend to alongside words. From the model's perspective it is all one stream.

This opens up work that was previously out of reach: asking questions about a screenshot, extracting structured data from a scanned invoice or a photographed receipt, describing a chart, reviewing an interface mockup, reading handwriting, or debugging from an error screenshot. Voice interfaces built on audio input and speech output are the other large category.

Two practical notes. Images consume input tokens, often a substantial number depending on resolution, so a prompt carrying several high-resolution images can be expensive : check how your provider counts them. And treat image understanding as strong but imperfect: models read charts, dense tables, and small text less reliably than they read prose, so verify extracted figures rather than trusting them.

Keep one distinction clear as well. A multimodal understanding model takes an image as input and answers in text. An image generation model produces pictures from a description and is a different kind of system, even when both are offered behind a single product.

Putting It Together: A Practical First Week

Reading about LLMs has sharply diminishing returns compared with using them. A concrete progression through the four parts above:

  1. Day 1. Take a task you already do : drafting a reply, summarizing notes, cleaning a list : and do it with a chat assistant. Note where the first output misses.
  2. Day 2. Rewrite that prompt three times, adding audience, format, and exclusion constraints. Compare the results side by side.
  3. Day 3. Convert it to a proper system-plus-user structure. Move the durable rules into the system message.
  4. Day 4. Run your text through a tokenizer. Count the tokens, then estimate what a thousand requests would cost using the formula in Part 3.
  5. Day 5. Build a few-shot prompt that returns valid JSON every time. Then remove examples one at a time and see how far you can go before quality drops.
  6. Day 6. Paste a long document into the context and ask questions against it. Notice what happens to answers about material near the middle.
  7. Day 7. Assemble twenty test inputs for your task and score your prompt against all of them. You now have an evaluation set, which puts you ahead of many people shipping LLM features.

From here, the natural next topics are retrieval-augmented generation for grounding models in your own documents, tool use and function calling for letting a model reach live data and take actions, and systematic evaluation for keeping quality stable as you change things.

Glossary

  • Token : the unit of text a model processes; roughly three-quarters of an English word.
  • Tokenization : splitting text into tokens and mapping them to vocabulary IDs.
  • Parameter : one of the billions of learned numbers that constitute the model.
  • Embedding : a numeric vector representing meaning, where proximity implies similarity.
  • Transformer : the neural network architecture underpinning modern LLMs.
  • Attention : the mechanism letting each token draw on relevant other tokens.
  • Context window : the total tokens a model can consider at once.
  • System prompt : the message setting persistent behaviour and constraints for a conversation.
  • Zero-shot / one-shot / few-shot : prompting with no examples, one example, or several.
  • In-context learning : adapting behaviour from examples in the prompt, without changing parameters.
  • Pretraining : the initial large-scale next-token training phase.
  • Fine-tuning : additional training on a narrower dataset to specialize behaviour.
  • RLHF : reinforcement learning from human feedback, used to align output with human preferences.
  • Training cutoff : the date beyond which a model has seen no data.
  • Hallucination : confident, fluent, false output.
  • Chat model : a model that takes messages and generates text.
  • Embedding model : a model that converts text into vectors for comparison, generating no text.
  • Open-weight model : a model whose trained parameters are published for download.
  • Multimodal model : a model accepting more than one input type, such as images with text.
  • RAG : retrieval-augmented generation; fetching relevant documents and supplying them as context.

Frequently Asked Questions

Do I need a machine learning background to use an LLM?

No. Using an LLM through a chat interface or an API requires no machine learning knowledge. Clear writing, a habit of verifying output, and ordinary programming skill cover the great majority of applications.

What is the difference between a system prompt and a user prompt?

The system prompt sets persistent behaviour, role, and constraints for the whole conversation. The user prompt carries the specific request for one turn. Durable rules belong in the system message so they do not have to be repeated.

When should I use few-shot instead of zero-shot prompting?

Start zero-shot. Add examples when output format is inconsistent, when edge cases are handled wrongly, or when you need a specific tone or labelling convention. Examples are charged on every request, so add them only where they demonstrably improve quality.

How do I estimate what an LLM feature will cost?

Count input tokens (system prompt plus examples plus user content) and expected output tokens for a typical request, divide each by a million, multiply by the provider's respective rates, and add them. Then multiply by expected monthly volume. Fixed overhead such as few-shot examples is charged every single time.

Is a larger context window always better?

No. Long contexts cost more, respond slower, and models use material in the middle of a long input less reliably than material at either end. Supplying the right few thousand tokens usually beats supplying everything.

What is the difference between a chat model and an embedding model?

A chat model generates text for a person to read. An embedding model produces vectors used to measure similarity between pieces of text, and generates no text at all. Search and clustering need embeddings; writing and answering need a chat model. Many systems use both together.

Should I use an open-weight model or a hosted API?

Prototype on a hosted API, which removes all infrastructure work from the learning curve. Consider open-weight models once you know your volume, latency requirements, and data-residency constraints : particularly if input data cannot leave your environment, or if high volume makes self-hosting cheaper.

Why does the model give a different answer each time?

Token selection samples from a probability distribution rather than choosing deterministically. Lowering the temperature setting reduces variation considerably, though it does not guarantee byte-identical output.
